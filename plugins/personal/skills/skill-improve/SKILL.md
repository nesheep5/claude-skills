# skill-improve — 指摘をスキルに反映する

スキルの出力に対する指摘は、放っておくと毎回手で直すことになる。指摘をログに溜め、`スキル × 節` で集計して SKILL.md 自体を直す。

**扱うのは「スキルの手順や観点の不備」だけ。** その案件固有の事情は記録しない。判定基準は「次に別の対象で同じスキルを使ったとき、同じ指摘が再発するか」。再発するならスキルの不備、しないなら案件固有。

## ログ

`~/.claude/skill-feedback/log.jsonl`。ローカル専用で git 管理しない（案件由来の記述がリポジトリに入るのを防ぐ）。ディレクトリが無ければ作る。

1行1 JSON。**追記のみ**で、既存行の書き換え・削除をしない。

| フィールド | 型 | 内容 |
|---|---|---|
| `id` | string | `<日付>-<連番>`（例 `2026-01-01-1`）。同日の `id` の最大連番 +1（末尾行が過去日の `applied` 追記であることがあるため、末尾だけ見ない） |
| `date` | string | 記録日 `YYYY-MM-DD` |
| `skill` | string | 対象スキル。プラグイン配下は `<plugin>:<name>`（例 `dev-docs:prd`）、素のスキル・プロジェクトスコープはスキル名のみ（例 `my-skill`）。集計キーなので表記を揺らさない |
| `section` | string | 成果物の節見出し。対象スキルの「構成」に列挙されたものを使う。節に紐づかない指摘は `(全体)` |
| `issue` | string | 何が問題だったか。1〜2文 |
| `fix_hint` | string | どう直せば再発しないか。**ユーザーの言葉を優先する**（言い換えると意図が落ちる） |
| `applied` | string | 反映したときだけ付ける。反映日 `YYYY-MM-DD` |

```json
{"id":"2026-01-01-1","date":"2026-01-01","skill":"dev-docs:tech-research-doc","section":"(全体)","issue":"読者が既に知っている情報が先頭に来ていた","fix_hint":"誰に対する何を決める資料かを先に固め、読者が知っていることは付録へ送る"}
```

反映後は元の行を書き換えず、同じ `id` で `applied` を付けた行を追記する。読むときは同 `id` の**最後の行**を有効とみなす。

## 記録するタイミング

スキルが生成した成果物に対し、ユーザーが指摘・修正を返したとき。次を満たす指摘だけ記録する。

- **スキルの手順や観点の不備**に起因する（その案件だけの事情ではない）
- ユーザーに「これはスキルに反映しますか」と一言確認してから追記する

案件固有の語（社名・製品名・顧客名）を `issue` / `fix_hint` に入れない。

## 対象スキルの探し方

`skill` から SKILL.md の実体を引く。**編集とコミットは必ず実体側で行う**。

```bash
# プラグイン配下（<plugin>:<name>）: マーケットプレイスの読み込み元を引く
jq -r 'to_entries[] | "\(.key)\t\(.value.installLocation)"' ~/.claude/plugins/known_marketplaces.json
# ローカルのパスで登録したマーケットプレイスなら、実体は次の場所
ls <installLocation>/plugins/<plugin>/skills/<name>/SKILL.md
# 素のスキル（<name>）
realpath ~/.claude/skills/<name>/SKILL.md
# プロジェクトスコープ
ls <project>/.claude/skills/<name>/SKILL.md
```

`installLocation` が `~/.claude/plugins/marketplaces/` 配下のもの（GitHub から入れたもの）は複製で、編集しても次の更新で消える。編集せず、改善案の報告にとどめる。

実体を含む git リポジトリが編集対象。`git -C "$(git -C "$(dirname <実体パス>)" rev-parse --show-toplevel)"` でコミットする。公開リポジトリなら、push の前にそのリポジトリの CLAUDE.md にある公開前レビューを通す。

## 手順

1. **ログを読む**: 無い・空なら「まだ記録が無い。スキルで成果物を作り、指摘を返すと記録される」と案内して終了
2. **有効な行を求める**: 同じ `id` の行が複数あれば最後の行を有効とみなす。`applied` 付きは除外する。残らなければ「未反映の指摘は無い」と伝えて終了
3. **集計する**: `skill` → `section` でグループ化し、件数の多い順に並べる。同じ `section` に複数の `issue` があればまとめて見せる
4. **修正案を提示する**: グループごとに「対象ファイル / 節 / 現状の記述 / 提案する変更 / 根拠となる issue と fix_hint」を示し、**1グループずつユーザーの承認を取る**。承認されないものは飛ばす（ログには触らない）
5. **編集する**: 承認されたものを `superpowers:writing-skills` の流儀で編集する。下の「編集の要点」に従う
6. **applied を記録する**: 編集したグループの各 `id` について、元の行の内容に `applied: <今日の日付>` を加えた行をログ末尾に追記する。元の行は書き換えない
7. **コミットする**: 変更した SKILL.md をリポジトリごとにコミットする。メッセージは `<skill> の <section> にフィードバックを反映する`。push はしない

## 編集の要点

- **一般論を足さない。** 指摘の具体（数値の例、問い直しの文言、読者の呼び方）をそのまま入れる。「適切に書く」は指摘を反映したことにならない
- **形を指摘の型に合わせる。** 守られなかった規則なら禁止＋言い換え表、出力の形が違っていたなら「何を・どの順で書くか」の型、要素の欠落なら構成テンプレートの必須項目として埋め込む。欠落を散文の注意書きで補っても次回また落ちる
- **既存の記述を置き換えられるなら置き換える。** SKILL.md を足し算で伸ばさない
- **description は変えない**（トリガー精度に影響する）。変える必要があれば別途相談する
- 1件しか無くても手順の不備が明らかなら反映してよい。件数は優先順位の目安にすぎない
- `issue` / `fix_hint` に案件固有の語が混ざっていたら、SKILL.md には汎化した形で書く
