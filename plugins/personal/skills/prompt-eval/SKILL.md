# prompt-eval

CLAUDE.md の変更が「狙いどおり効いているか」と「他を壊していないか」を、before / after を実際に走らせて数えて確かめる。読んで良さそうに見えることと、モデルがその通りに動くことは別物なので、書いた人の感覚ではなく実行結果で判断する。

評価は数ドルかかり、ユーザーの承認を挟む。ユーザーと対話しながら進める前提のスキル。

## 評価するか省くか

挙動が変わりうる変更は評価する。規則の追加・変更・削除、言い換え、圧縮、並べ替え（優先順位が変わりうる）が該当する。

省いてよいのは挙動に影響しない変更だけで、誤字・リンク先・表記ゆれの修正がそれにあたる。省くときは理由をユーザーに 1 行で伝える。

## 手順

### 1. 対象と版を決める

- `--mode global`: `~/.claude/CLAUDE.md`、またはそこから `@import` されるファイル。`--file` には実際に編集するファイルを渡す。ランナーは入口の `~/.claude/CLAUDE.md` から行頭単独の `@path` を展開して組み立て、対象ファイルの部分だけ版を差し替える
- `--mode repo`: リポジトリ内の CLAUDE.md（複数可）。HEAD の git worktree をリポジトリの外に腕ごとに作り、対象ファイルだけ各版で上書きして cwd にする。本来の経路で読ませるので、差し込み位置の問題は無い。対象ファイル以外の未コミットの変更は両腕に入らない
- 版の既定は before=`HEAD`、after=`worktree`（作業ツリー）。一部だけステージしたなら `--after-ref index`、過去の変更を検証し直すなら `--before-ref <sha>^ --after-ref <sha>`

### 2. 期待する違いを書く（編集の前でも後でもよい）

期待する違いとは、「after ではこう振る舞い、before ではそうならないはず」を 1〜3 文で書いたもの。

- **まだ編集していないとき**: 意図を聞いて期待する違いを書き、ケースを作ってから編集する
- **編集が済んでいるとき**: diff と意図から期待する違いを書き、結果を見る前に固める

意図が diff から読み取れなければユーザーに聞く。

### 3. ケースを書く

形式は [references/case-format.md](references/case-format.md) を読む。置き場は、対象ファイルのあるリポジトリの `evals/prompt-eval/<case>/`。グローバル CLAUDE.md の実体を別のリポジトリから `@import` しているなら、そのリポジトリに置く。git 管理外なら `~/.claude/evals/prompt-eval/` に置く。

良いケースの条件:

- **before では落ちる依頼にする。** 規則が無くても既定で満たされる依頼では差が出ず、何も確かめていない。規則が効く場面、つまり既定の振る舞いと規則がぶつかる場面を狙う
- **依頼文に規則を書かない。** 「file リンクで答えて」のように依頼で指示すると、before も通る
- **行動と中身で判定する。** 見出し・節名・特定の言い回しで判定すると、after の文面に寄せただけで通る。形で判定できるものは regex、できないものは llm grader にする。regex は費用がかからない
- **1 つの変更に 1〜3 ケース**
- **削除・圧縮の変更では、消す規則が担っていた振る舞いを regression ケースとして先に書く**

### 4. 走らせる前にユーザーの承認をもらう

次を見せて承認をもらう。

- 期待する違い
- 走らせるケース（change と、同じ evals にある regression の全件）
- 費用の見込みと上限

承認されたケースの内容がそのまま走らせる版になる。記録にはケースのハッシュが残る。結果を見たあとでケースを変えたら、報告でそのことを必ず明示する。ケースを結果に合わせて緩めると、評価の意味が無くなるため。

費用の目安（既定モデルの被験 1 回 $0.2〜0.3、llm grader 1 票 $0.02〜0.1）:

- change: 2 腕 × 3 回 ＝ 6 回
- regression: after だけ 3 回。落ちたときだけ before を 3 回足す
- `--calibrate`: ケースごとに 3 回足す

全体の上限は `--max-cost`（既定 $5）。上限に収まりそうにないときは、対象ファイルと同じ対象の regression に絞る。それでも超えるなら、どれを走らせるかユーザーに選んでもらう。

**global モードで `--calibrate` を勧める場面**: 次の規則は、差し込み位置の違い（後述）で効き方が変わりうる。承認をもらうときに勧め、使うかは費用と合わせてユーザーが決める。

- サブエージェント向けの規則
- 既定の振る舞いと衝突する規則
- 優先順位を決める規則

### 5. 走らせる

時間がかかるので、ユーザーとの対話を止めないよう background で走らせる。

```bash
python3 <このスキルのディレクトリ>/scripts/prompt_eval.py run \
  --mode repo --file <repo>/CLAUDE.md \
  --cases <repo>/evals/prompt-eval \
  --out <repo>/tmp/prompt-eval
```

主なオプション:

| オプション | 用途 |
|---|---|
| `--case <name>` | ケースを絞り込む |
| `--runs` | 回数を変える（既定 3） |
| `--calibrate` | global モードの較正（上記） |
| `--judge-model` | 判定役のモデル（既定 sonnet。小さいモデルは形式の違いで誤判定しやすい） |
| `--judge-votes` | 有効票の数（既定 1。無効票は `--judge-retries` 回まで引き直す） |
| `--jobs` | 並列数（既定 2） |

被験側は普段の既定モデルのまま走らせる。普段と違うモデルで測っても意味が薄いため。

`--out` は gitignore された `tmp/` 配下にする。記録には応答の全文が入るので、コミットしない。

### 6. 結果を読む

`summary.md` の判定:

| 判定 | 意味 | 次にすること |
|---|---|---|
| pass | change: after ≥ 2/3 かつ before ≤ 1/3。regression: after ≥ 2/3 | 中身を確かめて報告 |
| not-discriminating | change で after も before も通る | ケースが規則を試せていない。before で落ちる依頼に直すか、「規則が無くても既定でできる＝書く必要が薄い」とユーザーに伝える |
| fail | change: after が 2/3 に届かない。regression: after が落ち、before は通っていた（退行） | 落ちた実行の応答を読み、規則の書き方かケースの問題かを見分ける |
| unstable | regression で after も before も 2/3 に届かない | 退行ではなく、ケースが元から不安定。ケースを見直す |
| inconclusive | 使用量上限・タイムアウト・判定の失敗・費用上限で、有効な実行が足りない | 不合格ではない。原因を直して走らせ直す |

数字だけで判断しない。少なくとも次の実行は、`runs/<case>/<arm>/<n>/final.md` と `grading.json` の evidence を読む。

- 落ちた実行
- 合格した after の 1 件

grader は、キーワードだけ出て行動が伴わない応答を通すことがある（偽陽性）。逆に、規則どおりの応答を落とすこともある。判別しない grader の警告（`always-pass-both` / `always-fail-both`）が出た grader は、合否の根拠になっていない。判定役の生の出力は `judge/` にある。

較正の結果が `inconsistent` なら、そのケースでは差し込み方式での before/after の差を当てにしない。

### 7. 報告と後始末

ユーザーには次を短く伝える。

- 対象と版
- ケースごとの before / after の合格数と判定
- 読んで分かったこと（偽陽性や付随的な違反など）
- global モードなら暫定である旨と較正の結果
- 費用と記録の場所

pass した change ケースは `kind: regression` に書き換え、`added_in` に変更のコミットを書いて evals に残す。未コミットなら後で埋める。ケースは対象のリポジトリにコミットする。

fail のときは、規則を直す前にユーザーに結果を見せる。規則を直したら、同じケースで走らせ直す。

## この手法の限界

- **global モードの差し込み位置が本来と違う。** 本来の CLAUDE.md はメッセージ内の system-reminder として入る。global モードでは `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` で自動読み込みを止め、`--append-system-prompt-file` でシステムプロンプトに足している。cwd から上の CLAUDE.md 類も、同じ形で両腕に共通に入れる。そのため合格は暫定として扱い、疑わしい規則は `--calibrate` で確かめる
- **`-p` モードで測っている。** TUI の表示ではなく、応答の文章とツール呼び出しの記録で判定する
- **3 回は少ない。** 判定が割れたら `--runs 5` で確かめる
- **ランナー自身のテストは偽の claude で行う。** ランナーを変えたら `python3 -m unittest discover -s tests` を通す（API は呼ばない）
