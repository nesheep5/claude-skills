# 共通ルール

種別を問わず、dev-docs が書くすべての文書に当てる規則。良い文書の条件は 3 つある。読者が判断や行動に要ることを冒頭で受け取れること、見出しだけを追っても論旨がたどれること、書かれた事実を後から確かめられること。種別の reference やローカルルールと食い違ったときは、ローカルルール > 種別の reference > この文書の順で従う。

## 構成

### ピラミッド構造で、概要から詳細へ分解する

文書の頂点に結論を置き、その下に結論を支える根拠を漏れなく重なりなく並べ、各根拠をさらに詳細へ分解する。読者はどの深さで読むのをやめても、そこまでで完結した理解を持てる。章 → 節 → 段落の各レベルで同じ形にする。

### 冒頭の要約で、判断に要ることを渡す

文書の最初の数行（目安は 3〜5 行）だけで、読者が判断や行動に必要なことを受け取れるようにする。要約には結論・その理由の要点・読者に求めること（判断・承認・作業）を入れる。経緯や背景は入れない。

### 導入は「状況 → 問題 → 問い → 答え」

導入が要るときは、状況（読者も同意する現状）→ 問題（その状況で起きている困りごと）→ 問い（だから何を決めるのか）→ 答え（結論）の順で、短く書く。背景は答えにつながる分だけ書く。

### この文書が答える問いを冒頭で示す

論文が研究課題を冒頭で示すように、文書が答える問いを 1 文で示す（「ログ基盤を 3 案からどれにするか」「障害の再発を防ぐために何を変えるか」）。問いが書けない文書は、目的が定まっていない。

### 事実と解釈を分ける

調べた結果（事実）と、そこから言えること（解釈）を、節か文で分ける。解釈には、どの事実から導いたかを添える。読者は事実を受け入れたうえで、解釈に異論を出せる。

### 限界を書く

調べていない範囲、前提が崩れると結論が変わる条件、確かめられなかったことを書く。限界を書かない文書は、読者に過信させる。

### 結論先行

文書全体・節・段落のすべてで「答え → 理由 → 詳細」の順に書く。結論を先に知った読者は理由を「検証」として読めるが、結論が最後だと理由を「暗記」しながら読むことになる。

Before:
> 現在の実装では API 呼び出しごとに認証トークンを再取得している。トークン取得には平均 300ms かかり、一覧画面では 20 回の API 呼び出しが発生する。そのため、トークンキャッシュを導入したい。

After:
> トークンキャッシュを導入したい。現在は API 呼び出しごとにトークンを再取得しており（平均 300ms）、20 回呼び出す一覧画面では合計 6 秒の無駄が生じているためだ。

### 逆茂木型にしない

前提・背景・経緯を積み上げてから本題に入る構成（木下是雄『理科系の作文技術』の言う逆茂木型）を避ける。背景が本題より先に 3 段落以上続いたら、本題を先頭に出し、背景は「なぜなら」の位置に移す。

Before:
> 以前、通知基盤を刷新した。その際、外部ライブラリの都合で言語ランタイムを旧版に固定した。その後ライブラリが新版に対応し、固定の理由は消えた。ランタイムを新版へ上げたい。

After:
> ランタイムを新版へ上げたい。旧版に固定していたのは通知ライブラリが未対応だったためだが、その制約は解消した。

### 段落の先頭文に主張を置く

各段落の先頭文に、その段落の主張を置く。先頭文だけを拾い読みして論旨が通るのが完成形。先頭文が「ところで」「なお」で始まる段落は、構成を見直すサイン。

Before:
> なお、バッチ処理は毎晩 1 時に起動する。実行時間は平均 30 分で、週末は 70 分まで伸びる。次回のリリースで集計処理を追加する予定もある。このままでは朝 5 時の締め切りに間に合わなくなる。

After:
> バッチ処理は朝 5 時の締め切りに間に合わなくなる。毎晩 1 時起動で実行時間は平均 30 分、週末は 70 分に伸びる。ここに次回リリースの集計処理が加わるためだ。

### 節と節をつなぐ

各節の末尾か次の節の冒頭で、「なぜ次を読むのか」を 1 文で動機づける。見出しだけで話題が飛ぶと、読者は節ごとに文書の目的を推測し直すことになる。

Before:
> ## 検索 API は p95 で 1.8 秒かかっている
> 計測の結果、p95 は 1.8 秒だった。
>
> ## インデックスを 2 つ追加する

After:
> ## 検索 API は p95 で 1.8 秒かかっている
> 計測の結果、p95 は 1.8 秒だった。遅延の大半はインデックス未整備によるフルスキャンなので、次にインデックスの設計を示す。
>
> ## インデックスを 2 つ追加する

### 文書の目的を 1 つに絞る

説明（なぜこうなっているか）・手順（どうやるか）・参照情報（一覧・仕様）は読まれ方が違う。1 つの文書に混ぜない。混ざりそうなら文書を分けるか、参照情報を付録に移す。

### 書かないことを先に決める

書き始める前に、目的（誰が読んで、何を判断・実行するか）から「書くこと」と「書かないこと」を両方決める。書かないことの典型は次の 3 つ。

- 目的に効かない情報
- 読者に渡すべきでない情報。書き手と AI の間だけで交わした話、作業用のメモ、下書きの変遷、個人用ナレッジの書式（「学び」「未解決の論点」のような節）
- 書いていないことの列挙。「載せていないもの」と書くと、かえって注意を引く

隠すためではなく、目的に絞るためにやる。素材が手元に多いほど、決めておかないと混ざる。

## 見出し

### 見出しはメッセージ型で、その節の結論を言い切る

見出しには、その節で読者が受け取る結論を短い文で書く。見出しだけを上から読むと、文書全体の論旨がたどれる状態を目指す。

- 良い例: 「推奨は案 B。移行費用が最も小さい」「検索 API は p95 で 1.8 秒かかっている」
- 悪い例: 「はじめに」「〜とは？」「まとめ」「検討結果について」（中身が無い）、「推奨は案 B です。ただし前提条件付きで、移行の段取りによっては案 C も残ります」（長すぎて見出しの役をしない）

### ブログ調の見出しにしない

疑問形（「〜とは？」「なぜ〜なのか」）、呼びかけ（「〜してみよう」）、比喩（「〜の壁」）、煽り（「知らないと損する」）は使わない。見出しの語も、下の「用語」に従ってドメインの語から取る。

### 定型の節は名詞の見出しのままにする

「関連文書」「未決事項」「付録」「出典一覧」のように、どの文書にもある定型の節は名詞の見出しのままにする。結論を言う節ではないため。

### 会社テンプレートの見出しは書き換えない

会社やチームのテンプレートを使うときは、テンプレートの見出しの構成と文言をそのまま残す。メッセージ型は、テンプレートの見出しの下に置く小見出しにだけ当てる。

## 用語

### そのドメインで使われている語を使う

語は、上流文書・コード・用語集（ローカルルールの `glossary.md`）・利用者の発話から取る。比喩、気の利いた言い換え、独自の造語は使わない。書き手が自分で名付けた語は、読者が知らない語だ。

### 新しい語が要るときは合意してから使う

既存の語で言えない概念が要るときは、合意フェーズの「用語」で名前を提案し、利用者の合意を得てから本文に使う。

### 初出で定義する

読者が初めて見る語には、その場で 1 行の定義を付ける。比較表の列名、評価の記号、段階の名前、独自に作った観点名も同じ。前提ファイルや社内資料に定義があることは、文書に書いたことにならない。

### 同じ概念は同じ語で呼ぶ

「利用者 / ユーザー / エンドユーザー」が混ざると、読者は「別物か？」と迷う。言い換えの豊かさは、開発の文書では欠点になる。

## 根拠

### 一次情報に当たる

調べるときは、可能な限り一次情報に当たる。一次情報とは、公式ドキュメント、コード、原典の社内文書、元データのこと。要約・検索結果のスニペット・記憶で書かない。要約やダイジェストで知った事実は、原典まで遡る。

### 正当性を後からレビューできるようにする

調べた事実には出典を付け、読者が記載の正当性を後から自分で確かめられるようにする。「根拠: 公式ドキュメント」とだけ書いた根拠は、読者にとって根拠が無いのと同じ。書き方（4 区分と必須要素、推測と出典未確認の書き方、出典一覧）は `${CLAUDE_PLUGIN_ROOT}/references/citation-rules.md` に従う。

種別を問わず、調べた事実を含む文書すべてに当てる。調べた結果は文書とは別の調査記録に持ち、文書は調査記録から書き起こす（`${CLAUDE_PLUGIN_ROOT}/references/research-record.md`）。

### 評価には理由を書く

「〜が良い」「〜を推す」には、どの事実・どの要件からそう判断したかを添える。数値を並べて終わらず、「この観点はどの案でも決め手にならない」のように評価まで書き切る。

## 参照

### ID を振って ID で参照しない

要件・論点・観点に R1・T3 のような ID を振り、本文で ID だけを使って参照しない。一覧表に # 列も作らない。簡潔に書ける反面、読者は ID を見るたびに定義へ戻って中身を確かめることになる。要件や論点は短い名前（「最小権限」「スケール性」）で呼び、文書全体で同じ名前を使う。

### 前方参照をしない

「詳細は後述」「第 5 章で説明する」を前提に読ませない。その場で理解に要ることは、その場で書く。後ろの節を読まないと前の節が分からない構成は、構成の誤り。

## 文

### 一文一義

1 文には 1 つの主張だけを入れる。「〜であり、〜だが、〜なので」と接続助詞でつながった文は分ける。60 字を超えた文は分けることを検討する。

Before:
> 現行の同期処理は実装が単純で運用実績もあるが、件数が 1 万を超えるとタイムアウトするので、非同期化してジョブキューに逃がす案を検討している。

After:
> 現行の同期処理は件数が 1 万を超えるとタイムアウトする。実装の単純さと運用実績は利点だが、この上限は許容できない。非同期化してジョブキューに逃がす案を検討している。

### 能動態で書く

「〜される」「〜と考えられる」より「〜する」「〜と考える」。主語のない受動態は、誰がやるのかを読者に推測させる。

### 削って意味が変わらない語は削る

よく出る冗長な言い方と、その直し方。

- 「〜することができます」→「〜できる」
- 「〜を行います」→「〜します」
- 「〜という形になっています」→「〜になっている」
- 「〜する必要があります」→「〜が必要だ」
- 「〜だと考えられます」→「〜だ」（根拠があるなら断定する）
- 「まず最初に」→「まず」
- 「〜について説明します」→ 削って見出しに任せる

### 事実と意見を書き分ける

事実は断定で書き、意見は意見と分かる形（「〜と判断した」「〜を推す」）で書く。事実の記述に「〜のはずです」「おそらく」を混ぜない。

Before:
> 現行の全文検索は性能が悪いのでおそらく専用の検索エンジンに移行すべきです。

After:
> 現行の全文検索は、想定するデータ量で p95 が 2 秒を超える（負荷試験の結果）。目標の 500ms を満たさないため、専用の検索エンジンへの移行を推す。

### 箇条書きは並列な列挙にだけ使う

論理の流れ（A だから B、しかし C）は散文で書く。箇条書きは並列な列挙にだけ使い、ネストは 2 段まで。各項目が「〜のため」「しかし〜」で始まっていたら、それは散文で書くべき論理の展開。

Before:
> - インメモリの KVS はレイテンシが低いため第一候補になる
> - しかし永続化の設定が運用コストを押し上げる
> - そのため今回は既存 DB のキャッシュテーブルを採用する

After:
> インメモリの KVS はレイテンシが低く第一候補だったが、永続化設定の運用コストが見合わない。今回は既存 DB のキャッシュテーブルを採用する。

## AI 臭さ

次の 6 つは、AI が書いた文書に出やすく、読者の信頼を下げる。見つけたら書き直す。

- **同じ内容の反復**: 本文で述べたことを「まとめ」で言い換えて繰り返す。まとめは削るか、本文に無い判断・次の行動だけを書く
- **空疎な前置き**: 「重要なのは」「注目すべき点として」。前置きを削り、中身から書き始める
- **過剰なヘッジ**: 「一般的には〜と言われています」「〜かもしれません」の多用。根拠を確かめて断定するか、「未確認」と明記する
- **中身のない総括**: 「適切に設計することが重要です」。何をどうするのが適切かを具体的に書く。書けないなら削る
- **過剰な強調**: 太字の乱発、絵文字、「非常に」「極めて」。強調は 1 節に 1 か所まで。程度の副詞は数値に置き換える
- **箇条書きの乱用**: 3 行の散文で書ける説明を 5 項目のリストに分ける。論理の流れは散文に戻す
