# 付随文書

コードの変更に付いて回る短い文書を書く・直すときの規則。対象は commit message・PR 説明・エージェント向けの指示（CLAUDE.md・AGENTS.md・SKILL.md など）・コードコメントの 4 つ。

## 流れ

合意フェーズ・調査記録・下流チェックは回さない。形はリポジトリの規約で決まっていて、書く事実は差分とコードから取れるためだ。

1. 規約を読む。リポジトリの CLAUDE.md・CONTRIBUTING・PR テンプレート（`.github/pull_request_template.md` など）・`git log` の直近の書きぶりを見て、ローカルルールを `${CLAUDE_PLUGIN_ROOT}/references/local-rules.md` に従って読む。規約があれば、この reference より規約を優先する
2. 事実を差分とコードから取る。commit と PR 説明は `git diff` と `git log`、コメントは対象のコード、エージェント向けの指示は実際の構成やコマンドを確かめる。会話で聞いただけの事実を書かない
3. 書く。共通ルール（`${CLAUDE_PLUGIN_ROOT}/references/writing.md`）のうち、結論先行・一文一義・削って意味が変わらない語は削る・事実と意見を書き分ける・AI 臭さを当てる。ピラミッド構造・導入の型・見出しの型は当てない
4. 突き合わせる。書いた内容に、差分に無い変更・実際と違うコマンドやパス・もう無い挙動が入っていないかを確かめる

## commit message

- 1 行目に何を変えたかを書く。`git log` の書きぶりに合わせるのは、言語・接頭辞・1 行目の長さまで。本文の書き方は、明文の規約（CONTRIBUTING など）が無ければ、直近の commit が作業の一覧であってもこの節に従う
- 本文には、なぜ変えたかと、差分から読み取れない判断を書く。差分を読めば分かる What を言い換えない。変更したファイルや作業の一覧を並べない
- 1 つの commit に 1 つの目的。目的が 2 つあるなら、分けることを提案する

## PR 説明

- テンプレートがあれば、見出しの構成と文言をそのまま使う
- 冒頭に背景を書く。なぜこの変更が要るか（課題・経緯・目的）と、関連するチケットや議論へのリンク
- 変更内容は、レビュアーが差分を読む順の道案内として書く。ファイルごとの言い換えにしない
- 動作確認には、CI で担保できない確認（画面の表示、API の応答、操作の流れ）だけを書く。単体テストで担保できることは書かない
- 既存の PR 説明を直すときは、今の差分と食い違う記述を残さない。追加した commit の内容も反映する

## エージェント向けの指示

読み手はモデル。人に向けた導入や要約より、従うべき規則を短く書く。

- 命令の形で書き、規則ごとに理由を 1 文添える。理由があると、書いていない状況にも規則を当てられる
- 同じ規則を複数の場所に書かない。正本を 1 つに決め、ほかからは参照する
- 推敲で削るのは、重複と冗長な言い換えだけにする。規則に添えた理由と判断の基準は削らない。基準を別の箇所への参照に置き換えるときは、読み手（サブエージェントなど、そのファイルの一部しか渡されない相手を含む）が参照先を見られるかを確かめる
- コードやディレクトリ構成を読めば分かることは書かない。読んでも分からない判断・禁止事項・手順を書く
- SKILL.md の description には、何をするかと、どんな依頼で使うか・使わないかを書く。モデルはここだけを見て呼ぶかを決める

## コードコメント

- 残すのは、コードを読んでも分からない why（制約、設計上の理由、外部の仕様に合わせた箇所）
- 処理の言い換え・経緯・チケット番号・変更の説明（「今回追加」など）は書かない。経緯は commit と PR に書く
- 定数・型・セクションのラベルは、コードの目次として残してよい
- 周りに同じ形のコメントがあれば、その書きぶりと粒度に合わせる
