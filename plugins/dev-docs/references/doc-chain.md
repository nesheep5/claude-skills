# 文書の連鎖と引き渡し情報

5 つの種別は、上流から下流へ次の順に流れる。下流の文書は上流の文書をインプットにするため、上流には下流が必要とする情報が具体的に書かれている必要がある。流れの「下流チェック」は、この文書を正として回す。

```
Brief ──▶ PRD ──▶ DesignDoc ──▶ 開発スケジュール
                     ▲
                 検討資料
```

- Brief（`brief`）: なぜやるか
- PRD（`prd`）: 何を提供するか
- 検討資料（`research`）: 調査をもとに何を選ぶか
- DesignDoc（`design-doc`）: どう作るか
- 開発スケジュール（`dev-schedule`）: いつ何を出すか

打ち合わせ資料（`meeting`）と依頼書（`request`）は、この連鎖の外にある。下流チェックは、それぞれの reference の「下流に渡すもの」だけを確かめる。

## 引き渡し情報

### Brief → PRD

- 下流が必要とする情報: 解く課題、対象ユーザー、成功指標（数値）、やらないこと
- 欠けているとき: PRD の概要で仮置きし、未決事項に「Brief で確定させる」を載せる

### PRD → DesignDoc

- 下流が必要とする情報: 優先度付きの機能要件（Must / Should / Could）、非機能要件（性能・可用性・セキュリティの目標値）、制約と前提、受け入れ条件
- 欠けているとき: DesignDoc の現状と課題で仮置きし、未決事項に判断者 PdM で載せる

### 検討資料 → DesignDoc

- 下流が必要とする情報: 採用する方針、却下した案と理由、未決事項
- 欠けているとき: DesignDoc の検討した代替案に「調査未実施」と書く

### 検討資料 → Brief

- 下流が必要とする情報: 選んだ案、対象ユーザー、前提条件、落とした案と理由
- 欠けているとき: Brief の背景と課題で仮置きし、未決事項に「調査結果から確定させる」を載せる

### PRD + DesignDoc → 開発スケジュール

- 下流が必要とする情報: 要求の優先度、コンポーネントの分割、コンポーネント間の依存、外部依存（審査・他チーム）
- 欠けているとき: フェーズを切れないので、先に DesignDoc の該当する節を埋めるよう促す

## 下流チェックの回し方

自分の文書が上流に当たる項目を見て、下流が必要とする情報が文書中に具体的に書かれているかを確かめる。「性能を考慮する」のような具体値の無い記述は、欠けとみなす。欠けは削らず未決事項に落とし、判断者を書く。

既存の文書のレビューでは、指摘を「どの節に何が無いか」と「下流のどの文書が困るか」をセットで返す。
