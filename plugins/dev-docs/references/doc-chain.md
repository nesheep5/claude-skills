# 文書の連鎖と引き渡し情報

dev-docs が扱う5種の文書は次の順で上流から下流へ流れる。下流の文書は上流の文書をインプットにするため、上流には「下流が必要とする情報」が埋まっている必要がある。この表が種別スキルの**下流チェック**の正である。

```
Brief ──▶ PRD ──▶ DesignDoc ──▶ 開発スケジュール
                     ▲
               検討資料
```

| 文書 | 問い | 主な書き手 | スキル |
|---|---|---|---|
| Brief | なぜやるか | PdM | `/dev-docs:brief` |
| PRD | 何を提供するか | PdM | `/dev-docs:prd` |
| 検討資料（技術調査資料） | どれに進むか / どの技術方針を採るか | エンジニア | `/dev-docs:tech-research-doc` |
| DesignDoc | どう作るか | エンジニア | `/dev-docs:design-doc` |
| 開発スケジュール | いつ何を出すか | エンジニア + PdM | `/dev-docs:dev-schedule` |

## 引き渡し情報

| 上流 → 下流 | 下流が必要とする情報 | 欠けているときの扱い |
|---|---|---|
| Brief → PRD | 解く課題 / 対象ユーザー / 成功指標（数値）/ やらないこと | PRD の「概要」で仮置きし、未決事項に「Brief で確定させる」を載せる |
| PRD → DesignDoc | 優先度付き機能要件（Must / Should / Could）/ 非機能要件（性能・可用性・セキュリティの目標値）/ 制約・前提 / 受け入れ条件 | DesignDoc の「現状と課題」で仮置きし、未決事項に判断者 PdM で載せる |
| 検討資料 → DesignDoc | 採用方針 / 却下案と理由 / 未決事項 | DesignDoc の「検討した代替案」に「調査未実施」と書く |
| 検討資料 → Brief | 選んだ案 / 対象ユーザー / 前提条件 / 落とした案と理由 | Brief の「背景と課題」で仮置きし、未決事項に「調査結果から確定させる」を載せる |
| PRD + DesignDoc → 開発スケジュール | 要求の優先度 / コンポーネント分割 / コンポーネント間の依存 / 外部依存（審査・他チーム） | フェーズ分割ができないので、先に DesignDoc の該当節を埋めるよう促す |

## 下流チェックの回し方

種別スキルの段階4で、自分の文書が「上流」に当たる行を見て、各項目が文書中に**具体的に**書かれているか確認する。「性能を考慮する」のような具体値のない記述は欠けとみなす。欠けは削らず「未決事項」の表に落とし、判断者を書く。

既存文書のレビュー・追記を頼まれたときは、この段階だけを回す。指摘は「どの節に何が無いか」と「下流のどの文書が困るか」をセットで伝える。
