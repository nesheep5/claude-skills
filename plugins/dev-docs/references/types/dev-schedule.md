# 開発スケジュール

この文書が答える問い: PRD の要求を、どの順で、どれだけの期間で出すか。

エンジニアと PdM が、開発のフェーズ分割・マイルストーン・期間に合意するための文書。見積の精度より、フェーズの切り方の根拠と、見積が崩れる条件が書かれていることを優先する。上流は PRD と DesignDoc。PRD の優先度付きの機能要件と、DesignDoc のコンポーネント分割・依存関係が無いとフェーズを切れない。無い場合はそのことを伝え、前提質問で最低限を補う。

## 前提質問

決まっていないものを 1 問ずつ聞く。見積の粒度は必ず聞く。

- 見積の粒度はどれか: 人日の積み上げ / スプリント（N 週）単位 / 月単位
- 人員は何人か。並行して抱えている他のタスクはあるか
- 固定の期日（契約・イベント・法規制の施行日）はあるか
- 最初に価値を出したい要求はどれか（PRD の Must の中でも順序があるか）
- 技術的に不確実で、早めに確かめたい部分はあるか（DesignDoc の未決事項から拾う）
- 外部依存（ストア審査・他チームの API・データ提供）と、そのリードタイム

## 必須の情報

- **見積の粒度**: 人日 / スプリント / 月。期間の単位をこれに揃える
- **フェーズ分割の方針**: 早期の価値 / リスクの先取り / 依存の解消 のどれを優先したか。「段階的に」だけでは方針ではない
- **フェーズごとの中身**: 含める要求（PRD と同じ要求名）・完了条件（確かめられる状態）・期間・依存。1 フェーズに Must を詰め込みすぎていないか（後半のフェーズが Could だけなら、前半が重すぎる）
- **マイルストーン**: その時点で成立している状態。日付が決められなければ相対（開始から N 週）
- **見積の前提とリスク**: 人員・並行タスク・外部依存。「この前提が崩れると N 週延びる」の形で、見積が崩れる条件を並べる。前提が書かれていない数字は、崩れたときに誰も気づけない
- **バッファ**: 人日で積み上げる場合は別の行で明示する。粒度が粗い場合は幅（2〜3 スプリント）で書いてよい

## たたき台の目次

合意フェーズで組み替える出発点。見出しは、その節の結論を言い切る文に置き換える。

```markdown
# <機能名> 開発スケジュール
- 作成日 / 作成者 / ステータス
- 関連文書: PRD / DesignDoc
- 見積の粒度: <人日 / スプリント / 月>

<冒頭の要約: 全体の期間、最初に出すもの、見積が崩れる最大の条件を 3〜5 行>

## <切り方の方針を言い切る（例: 不確実な外部連携を第 1 フェーズで確かめ、画面は後に回す）>
## <フェーズの中身を言い切る（例: 3 フェーズ・計 8 週で Must をすべて出す）>
| フェーズ | 含める要求 | 完了条件 | 期間 | 依存 |
## <節目を言い切る>
| 時期 | 成立している状態 |
## <見積が崩れる条件を言い切る（例: 他チームの API の提供が 2 週遅れると全体が 2 週延びる）>
## 未決事項
| 論点 | 推し | 判断者 |
```

mermaid の gantt は任意。

## 下流に渡すもの

連鎖の末端なので、下流の文書は無い。代わりに上流との整合を確かめる。PRD の Must の要求がすべてどこかのフェーズに含まれているか、DesignDoc の依存関係とフェーズの順が矛盾していないか。矛盾は未決事項に落とす。
