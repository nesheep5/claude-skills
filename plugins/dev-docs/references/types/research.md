# 検討資料

この文書が答える問い: 調べた結果から、誰が、何を、どう決めるか。

調査結果をもとに、誰かが何かを決めるための資料。技術方針の選定（認証方式・ライブラリ・DB・アーキテクチャ・SaaS / API）に限らず、事業・製品・施策の選択でも同じ作法を使う。調べた結果は先に調査記録（`research-record.md`）に書き、資料はそこから書き起こす。

良い検討資料の条件は 4 つ。

- 読者が決めることが先頭にある。資料は読者の判断の順に並び、書き手の作業の順には並ばない
- 結論だけでなく検討の過程が追える。却下した案とその理由、検証の経緯が残っている
- 初見の読者が前後を行き来せずに読める
- 事実と意見が分かれ、事実には出典がある

## 前提質問

決定を左右する前提を、書き始める前に 1 問ずつ確かめる。前提が 1 つ変わると結論が反転することが多い。

読者と判断（ここが空なら書き始めない）:

- 読者は誰か。その人は何を決めるのか。選択肢は何件か
- 読者が既に知っていることは何か（本体に書かず付録へ送る）
- 判断の前提として読者に渡すべき条件は何か（期限、許容コスト、評価の時間軸、やらない領域）

対象と制約:

- 対象は誰の環境・データか（自社 / 顧客 / 混在）
- スケール感（ユーザー数・頻度・データ量）。未定なら未定と書く。未定であること自体が「上限を先に把握すべき」という検討の動機になる
- UX・運用の制約（利用者が自力で導入するか支援が要るか、少人数のチームか）
- 機密性・コンプライアンスの要求
- 将来の要件（今は不要だが後で欲しくなるもの）

## 必須の情報

- **判断の枠**: 誰が・何を・どの選択肢から・何を前提に決めるか。冒頭の 4〜6 行で渡す。経緯や背景を積む場所ではない
- **推し案**: エンジニアとしての推しと、その理由。理由は下の観点に対応づける。受け入れるトレードオフも正直に書く
- **観点の定義**: 評価の軸ごとに「何を評価するか」「なぜ重要か」。「なぜ重要か」は要件や前提に接続する。観点を事実より先に置くのは、調べた事実が唐突に現れるのを防ぐため。「上限の数値」をいきなり見せられた読者は「で、これは問題なのか」と迷う
- **案ごとの整理**: 事実と評価は観点別ではなく案別にまとめる（読者は「この案を採るとどうなるか」を知りたい）。各案に、仕組みの 1 行説明 → 調べた事実（出典つき）→ 評価 → 制約
- **評価は全案共通の行の順で**: 案ごとに同じ観点を同じ順で並べる。行の位置だけで案どうしを比べられる。メリット / デメリットの列挙は使わない。評価の記号には凡例を最初に示す（◎ 強み / ○ 満たせる / △ 条件付き・実装でカバー / × 満たせない・重い制約）
- **制約を独立して示す**: 工夫で回避できない条件（保存期間の上限、使えるリージョン、1 時間あたりの API 呼び出しの上限）を、デメリットと混ぜずに独立させる。意思決定で最も重い
- **却下した案と理由**: 「一見理想的だが、この仕様が要件と相容れないため除外」まで書く。読者が同じ案を再検討する無駄を防ぐ。「現実的か」が争点になった案は、論点と検証結果の組で経緯を残す
- **図を 1 枚以上**: 全案 × 判断を分けた観点の比較マトリクスか、次の一手が分岐するときの流れ図。図のセルにも出典を求める。根拠を示せないセルは「未確認」と置く。調査の規模を示す図（候補 N 件 → M 件）は作らない
- **次の一手**: 推しを選んだ場合に最初にやること。費用と期間
- **未決事項**: 決めきれない論点を、推しと判断者つきで
- **調べた事実の出典**: `citation-rules.md` に従う。調査時点の日付を書く。料金・上限のように改定されうる情報は「実装時に最新を確かめる」と添える

## たたき台の目次

どちらの型を使うかは、読者が何をするかで決める。合意フェーズで組み替える出発点で、見出しはその節の結論を言い切る文に置き換える。

### 案を比べる型（読者が選択肢から選ぶとき）

```markdown
# <テーマ> 検討資料
- 作成日 / ステータス（検討中・決定済み）

<判断の枠: 誰が何をどの選択肢から決めるか、前提条件。4〜6 行>

## <推しを言い切る（例: 推奨は案 B。移行費用が最も小さい）>
| 選択肢 | 概要 | 推奨 |
## <比較の結論を言い切る（例: 決め手は運用負荷と移行期間の 2 つ）>
  比較マトリクス。列名・記号・段階の定義をこの節に置く
## <観点を言い切る>
| 観点 | 何を評価するか | なぜ重要か |
## <案 A の評価を言い切る>
## <案 B の評価を言い切る>
## <除外した案と理由を言い切る>
## <次の一手を言い切る>
## 未決事項
| 論点 | 推し | 判断者 |
## 付録
  調査の規模・手法・手前で落とした案の一覧・出典
```

読者が選定の当事者（開発メンバー）で、要件の共有が判断の前提になるときは、判断の枠に機能要件（必須 / 将来 / 前提条件）を置き、推しの節を比較の後ろに下げてよい。読者が判断だけを下す立場（経営者・PdM・顧客）なら上の順のまま使う。

### 事実 → 要件 → ギャップの型（現状の何が足りないかを議論するとき）

```markdown
# <テーマ> 検討資料
- 作成日 / ステータス

<判断の枠: 誰が何を決めるか、結論となるギャップの要点。4〜6 行>

## <分かった事実を言い切る（例: 新しいランタイムでは 3 つの API が廃止される）>
## <考慮すべき要件を言い切る（例: このうち 2 つには置き換え先がある）>
## <現状とのギャップを言い切る（例: 置き換え先が無いのは 1 つだけ）>
## <埋め方の案と推しを言い切る>
## <次の一手を言い切る>
## 未決事項
| 論点 | 推し | 判断者 |
## 付録
```

どちらの型でも、次の 4 つは崩さない。

- 読者が決めることと結論が冒頭にある（判断の論点・未決事項を末尾だけに置かない）
- 観点や要件の定義が、事実の評価より先にある
- 事実は案ごと、または要件ごとにまとめる
- 調査の過程は付録に置く

## 下流に渡すもの

DesignDoc に渡す: 採用する方針、却下した案と理由、未決事項。事業・製品の判断なら Brief に渡す: 選んだ案、対象ユーザー、前提条件、落とした案と理由。詳細は `doc-chain.md` の「検討資料 → DesignDoc」「検討資料 → Brief」。
