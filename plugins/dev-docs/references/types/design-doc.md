# DesignDoc

この文書が答える問い: PRD の要件を、どう作れば満たせるか。そしてなぜその作り方なのか。

PRD の要件をどう実装するかを、エンジニア間と PdM とで合意するための文書。設計の正しさより、「なぜこの設計にしたか」が後から追えることを優先する。読者は、詳細を知りたい実装担当のエンジニアと、要件が満たされるか・トレードオフは何かを知りたい PdM の両方。上流は PRD と検討資料。PRD が無ければ「関連文書: PRD なし」と書き、PRD の引き渡し情報（優先度付きの機能要件・非機能要件・制約・受け入れ条件）を前提質問で補う。設計対象のコードが手元にあれば、質問の前に現状を読む。

## 前提質問

PRD と検討資料で決まっていないものを 1 問ずつ聞く。

- 既存システムのどこに手を入れるか。触ってはいけない部分はあるか
- 設計を縛る非機能要件はどれか（PRD の目標値のうち、設計に最も効くもの）
- データの所有者と保持期間。既存データの移行は要るか
- 外部サービス・他チームとの境界（API・イベント・バッチ）はどこか
- リリース方法（一括 / 段階 / フラグ）に制約はあるか
- 却下済みの案はあるか（あれば理由ごと「検討した代替案」に載せる）

## 必須の情報

- **設計方針**: 設計判断の軸を 2〜4 個。それぞれ要件か制約に接続する（「非機能要件の p95 500ms を満たすため、集計は事前計算に寄せる」）。「拡張性を考慮する」のような一般論なら書き直す。DesignDoc の中核
- **コンポーネント設計**: コンポーネントごとに責務 / インターフェース / 依存先。PRD の Must の要求がすべて、どこかのコンポーネントに紐づく。紐づかない要求は未決事項に落とす
- **データと API**: スキーマ変更・API 仕様・イベント定義。移行が要るデータは移行方法まで
- **検討した代替案**: 採らなかった案とその理由。検討資料があればリンクし、結論を引用する。無ければ「調査未実施」と書く。案が 1 つしか無かったなら「単一案。理由: 〜」と書く。空にしない。却下理由が残っていないと、レビューで同じ案を蒸し返される
- **非機能・運用・移行**: PRD の非機能要件と同じ観点の順で、設計でどう応えるか。監視・障害時の挙動・ロールバック・段階リリース。設計で満たせない目標値は隠さず未決事項に載せる
- **テスト方針**: どの層で何を確かめるか。受け入れ条件との対応
- **調べた事実の出典**: 現状・外部 API の制約や上限・既存コードの挙動には、`citation-rules.md` の書き方で出典を付ける

## たたき台の目次

合意フェーズで組み替える出発点。見出しは、その節の結論を言い切る文に置き換える。会社テンプレートがあるときはそちらを骨組みにし、ここの内容をテンプレートの該当する見出しの下に流し込む。

```markdown
# <機能名> DesignDoc
- 作成日 / 作成者 / ステータス（草案・レビュー中・合意済み）
- 関連文書: PRD / 検討資料 / 開発スケジュール（あれば）

<冒頭の要約: 何を作るか、PRD のどの要求に応えるか、採る方針。PdM はここまでで判断できるように 3〜5 行>

## <変えなければならない点を言い切る（例: 今の同期処理は 1 万件でタイムアウトする）>
## <方針を言い切る（例: 集計は事前計算に寄せ、画面は結果を読むだけにする）>
## <構成を言い切る（例: 新しいコンポーネントは集計ジョブ 1 つだけ）>
  コンポーネント構成図（mermaid）。既存と新規を区別する
## <各コンポーネントの責務を言い切る>
## <データと API の変更を言い切る>
## <採らなかった案と理由を言い切る（例: リアルタイム集計は性能目標を満たせず採らない）>
| 案 | 概要 | 採らなかった理由 |
## <非機能・運用・移行への応え方を言い切る>
## <テストの要を言い切る>
## 未決事項
| 論点 | 推し | 判断者 |
```

図は mermaid で書く。文書の共有先が mermaid を描けないときは、画像にする必要があることを利用者に伝える。

## 下流に渡すもの

開発スケジュールに渡す: コンポーネントの分割、コンポーネント間の依存、外部依存（審査・他チーム）。詳細は `doc-chain.md` の「PRD + DesignDoc → 開発スケジュール」。
