# 合意フェーズ

新規作成と大きな改稿では、本文を書く前に 4 つの項目を利用者と合意する。種別ごとの決まった構成は、その文書の議論の筋に合わないことがある。書いてから構成を直すより、目次の段階で直す方が安い。

小さな修正とレビューでは、このフェーズを省く。

## 示すもの

次の 4 項目を、1 つのメッセージにまとめて示す。利用者が直しやすいように、項目ごとに短く書く。

### 読者と目的

- 誰が読むか（役割で書く。「判断する開発責任者」「実装を引き継ぐエンジニア」）
- その人がこの文書で何を決める、または何をするか
- 読者が既に知っていること（本文に書かず、付録に送るか省く）

### 答える問い

この文書が答える問いを 1 文で書く（「ログ基盤を 3 案からどれにするか」）。

### 目次

見出しはメッセージ型で、本文にそのまま使う文言で書く（`${CLAUDE_PLUGIN_ROOT}/references/writing.md` の「見出し」）。各見出しに、その節で言うことを 1 行ずつ添える。階層は字下げで示す。

```markdown
- 推奨は案 B。移行費用が最も小さい — 3 案の比較の結論と、受け入れるトレードオフ
  - 案 B は既存のジョブ基盤をそのまま使える — 追加の運用が要らない根拠
  - 案 A は性能で勝るが移行に 3 か月かかる — 却下の理由
- 判断に要る前提は 2 つ — 期限と許容コスト
- 未決事項 — 判断者つきの論点
```

目次は、種別の reference にある「たたき台の目次」から始めてよい。ただし並び順は、この文書の問いと読者に合わせて組み替える。会社テンプレートがあるときは、テンプレートの見出しをそのまま使い、メッセージ型はその下の小見出しにだけ当てる。

確かめること:

- 見出しだけを上から読んで、問いへの答えまで論旨がたどれるか
- 最初の見出しに結論があるか
- 後ろの節を読まないと前の節が分からない並びになっていないか

### 用語

本文で使う主要な語を、出所つきで並べる。

```markdown
- 配信ジョブ: 溜まった通知をまとめて送る定期処理（出所: コード）
- 送信上限: 1 時間あたりに送れる通知の件数（出所: 上流文書）
- 再送窓: 失敗した通知を送り直す期間（新規提案）
```

出所は「用語集」「上流文書」「コード」「発話」「新規提案」のどれか。「新規提案」の語は、合意が取れるまで本文に使わない。

## 合意の取り方

- 利用者が直した点を反映し、変わった項目だけを示し直す。全項目を毎回出し直さない
- 「これで書いて」「OK」などの了承を得てから本文に進む
- 利用者が「任せる」と言ったら、示した内容で書き始める
- 合意フェーズで受けた指摘も、`${CLAUDE_PLUGIN_ROOT}/references/learning.md` に従って取り込む
