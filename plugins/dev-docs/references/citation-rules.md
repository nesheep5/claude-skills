# 出典の書き方

調査資料・DesignDoc・スパイク検証記録など、事実をもとに意思決定する文書に適用する。目的は、読者が各主張の正当性を**自分で一次情報に当たって確認できる**状態にすること。「根拠: 公式ドキュメント」とだけ書いた根拠は、読者にとって根拠が無いのと同じ。

## 根拠の 4 区分と必須要素

事実の直後に、次のどれかの区分で根拠を付ける。区分名だけで終わらせない。

- **公式ドキュメント**: URL + 該当セクション名、または該当箇所の短い引用（原文のまま 1 文以内）。URL は**実際に開いて記述の存在を確認してから**付ける。記憶や検索結果のスニペットで書かない
- **コード**: `path:line`。作業ツリー以外を指すときはブランチ名またはコミットハッシュを前置する（例 `origin/poc/foo:lib/bar.rb:42`、`a1b2c3d`）。実在と行番号を確認する
- **社内文書**（Confluence・Jira・Slack 等）: ページ ID または URL。要約・ダイジェスト経由で知った事実は、元ページまで遡って付ける
- **ライブラリ**: gem / パッケージ名 + バージョン + ソース URL（GitHub の該当ファイルまたは API リファレンス）

推測（一次情報から導いた判断）は「推測」と明記し、**何と何から導いたか**を 1 行添える。出典が取れない事実は「出典未確認（候補 URL: ...）」と明記する。「〜だろう」「〜のはず」で断定を曖昧にして逃げない（tech-writing「事実と意見の書き分け」）。

## 文書末尾の出典一覧

参照した全 URL を「URL / 何を確認したか / 確認日」で列挙する。公式とそれ以外を分ける。確認日は API の上限・審査制度・料金が改定されるため必須。

## 既存文書の出典を補強するとき

結論・構成・推し案・数値は変えず、出典の明記だけを行う。補強中に誤記や矛盾を見つけたら本文を書き換えず、その箇所に「⚠ 要確認: 〜」と注記して報告する。判断は文書の所有者に返す。

## subagent に調査を委譲するとき

subagent はこのファイルを読まない。委譲プロンプトに上の「4 区分と必須要素」「推測・出典未確認の書き方」「出典一覧」を**そのまま書いて渡す**。返答には「出典未確認として残した主張」と「⚠ 要確認を付けた箇所」を列挙させ、リードがそこだけ確認する。
