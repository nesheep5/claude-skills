# ローカルルール

プラグインの共通ルールと種別の reference に、利用者とプロジェクトのルールを重ねる。ローカルが持つのは差分（上書きと追加）だけ。スキルを丸ごと複製しない。複製すると正本が 2 つになり、どちらが効いているか追えなくなる。

## 置き場

U と P の実際の場所は、SKILL.md の「置き場の解決」で決まる。この文書では記号だけを使う。

- **利用者のローカル（U）**: 設定 `local_rules_dir` で指定したディレクトリ。未設定なら、プラグインのデータディレクトリ。データディレクトリはプラグインの更新では消えないが、アンインストールで消える
- **プロジェクトのローカル（P）**: プロジェクトのルートにある `.claude/dev-docs/`。コミットしてチームで共有するものとして扱う

## ファイル

U と P のどちらにも、次のファイルを置ける。無いファイルは読まない。

- `style.md`: 書き方の好み。文書・調査記録の置き場の指定もここに書く
- `glossary.md`: 用語集。U では `## <プロジェクト名>` の節ごとに分かれる。P はそのプロジェクトの語だけを持つ
- `templates/<id>.md`: 会社やチームの文書テンプレート（`<id>` は種別の id）
- `templates/<id>.guide.md`: テンプレートの各見出しを埋めるための記載ルール・追加の前提質問
- `types/<id>.md`: プラグインに無い種別の追加、またはプラグインの種別の上書き。書式はプラグインの `types/` と同じ
- `promote-candidates.md`: プラグイン本体に昇格させたい一般則の候補（U だけ）

## 読み方

依頼の見極めのときに読む。

1. U と P の `style.md` を読む
2. U の `glossary.md` のうち、作業中のプロジェクト（リポジトリのディレクトリ名）の節と、P の `glossary.md` を読む
3. 種別が決まったら、種別の reference を P の `types/<id>.md` → U の `types/<id>.md` → プラグインの `types/<id>.md` の順に探し、最初に見つかったものを使う
4. テンプレートを P の `templates/<id>.md` → U の `templates/<id>.md` の順に探す。あれば、同じ場所の `<id>.guide.md` も読む

重なったときは P > U > プラグインの順で優先する。

## テンプレートがあるとき

- テンプレートの見出しの構成（順序・階層）と文言をそのまま骨組みにする。見出しをメッセージ型に書き換えない
- メッセージ型は、テンプレートの見出しの下に置く小見出しにだけ当てる
- 種別の reference の「必須の情報」は、テンプレートの該当する見出しの下に流し込む
- テンプレートの中の記入者向けの説明（「〜してください」形式のコメントなど）は、成果物から消す。相談先やレビュー依頼の指示は、消す前に利用者への促しに変える
- `<id>.guide.md` の記載ルールと追加の前提質問に従う

## 書き込み

- U には、指摘の取り込み（`${CLAUDE_PLUGIN_ROOT}/references/learning.md`）で確認を挟まずに書き込む。U のディレクトリやファイルが無ければ作る
- P は読むだけにする。チームの共有ファイルなので、書き込むのは利用者に聞いて了承を得たときだけ
