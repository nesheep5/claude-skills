# 検討資料の作成

調査結果をもとに誰かが何かを決めるための資料を作る。対象は技術方針の選定に限らず、事業・製品・施策の選択でも同じ作法が使える。良い資料の条件は4つ:

1. **読者が決めることが先頭にある** — 誰が・何を・どの選択肢から決めるのかが冒頭で分かること。資料は読者の判断順に並び、書き手の作業順には並ばない
2. **結論だけでなく検討過程が追える** — 却下した案とその理由、検証の経緯が残っていること。読者は結論の妥当性を過程で判断する
3. **初見の読者が前後を行き来せずに読める** — 定義一覧に戻らないと意味が取れない参照や、動機の説明なく現れる事実がないこと
4. **事実と意見が区別され、事実には根拠がある** — 数値・制約・仕様には出典があり、推奨には理由があること

## 読者から設計する（書き始める前に決める）

構成を決める前に次の3つを確定し、資料の冒頭に書く。ここが曖昧な資料は、書き手の調査過程が前に出て読者の判断材料が後ろに回る。

- **読者は誰で、何を決めるのか。** 「開発責任者が、ログ基盤を3つの選択肢から決める」のように、判断者と判断対象と選択肢の数まで書く
- **読者が既に知っていることは何か。** それは資料の本体に書かない。調査の規模（候補件数・ラウンド数・期間）、手法の正しさ、書き手の苦労はたいてい読者が関心を持たない。付録に送る
- **読者が知らないと判断できないことは何か。** それが本体になる

判断材料でない情報を本体に置かない。調査の過程を見せたくなったら、それは書き手の関心であって読者の関心ではないかを確かめる。

## 進め方

### 1. 前提を固める（作成前に質問する）

決定を左右する前提を、書き始める前に1問ずつ確認する。前提が1つ変わると結論が反転することが多い（例: 「ログの保存先を自社で管理するか外部サービスに預けるか」で構成の候補が変わる）。確認する典型:

**読者と判断（全資料で必須。ここが空なら書き始めない）**

- **読者は誰か。その人は何を決めるのか。** 選択肢は何件あるか
- **読者が既に知っていることは何か。** 本体に書かず付録へ送る対象を特定する
- **判断の前提として読者に渡すべき条件は何か**（期限、許容コスト、評価の時間軸、やらない領域）

**対象と制約**

- 対象は誰の環境・データか（自社 / 顧客 / 混在）
- スケール感（ユーザー数・頻度・データ量）。未定なら未定と資料に書く — 未定自体が「天井を先に把握すべき」という検討動機になる
- UX・運用の制約（利用者が自力で導入するか支援が要るか、少人数チームか）
- 機密性・コンプライアンス要求
- 将来要件（今は不要だが後で欲しくなるもの）

### 2. 事実を調査する

- 公式ドキュメントを最優先で当たり、数値・上限・仕様は**出典 URL とセットで**記録する
- 調査時点の日付を資料に明記する（API の上限や利用規約・提供条件は変わる）
- 実運用の前例（同じ方式を使っている実サービス）は強い証拠になる。見つけたら手順まで確認して載せる
- 変わりやすい断定を避ける。プラン名・料金・上限など改定されうる固有情報は「対象プランのみ（実装時に最新を確認）」のように逃げ道を書く

### 3. 技術選定の観点を定義する

方式の優劣が分かれる評価軸を先に洗い出し、**観点ごとに「何を評価するか」「なぜ重要か」を書く**。「なぜ重要か」は要件・前提条件に接続する（例: 「スケール未定 → 後から方式を替えるコストは大きいので、天井の位置だけ先に把握する」）。よく使う観点:

性能 / 可用性 / セキュリティ（最小権限・データ分離）/ 外部依存性（仕様変更・提供終了など自社でコントロールできない要因）/ スケール性（上限と逃げ道）/ 保守運用（定常運用の重さ）/ 費用 / 移行容易性

観点を先に定義する理由: 調査事実が唐突に現れるのを防ぐため。「rate limit の数値」をいきなり見せられた読者は「で、これは問題なの？」と迷う。「スケール性の評価で共通の天井になるのが rate limit」という導入があれば迷わない。

### 4. アプローチ別に整理する

事実・評価は**観点別ではなくアプローチ別**にまとめる（読者は「この方式を採るとどうなるか」を知りたい）。各アプローチに: 仕組みの1行説明 → 調査事実（出典付き）→ 評価表 → 制約。

- **却下した案も理由付きで残す**。「一見理想的だが、この仕様が要件と相容れないため除外」まで書く。読者が同じ案を再検討する無駄を防ぐ
- アプローチ内のサブ論点（構成のバリエーション、データとアカウントの対応付けなど）は、その配下に置く
- 「現実的か？」が争点になった案は、**検証 Q&A**（論点 → 検証結果の表）として経緯を残す

### 5. 推し案とチームへの委任事項を書く

- **エンジニア目線の推し案**を明示する。理由は §3 で定義した観点に対応付け、**受け入れるトレードオフ**も正直に列挙する
- 自分たちで決めきれない論点は**未決事項の表**（論点 / 推し / 判断者）にして、誰が決めるかまで書く

### 6. 下流チェックとフィードバック

- `${CLAUDE_PLUGIN_ROOT}/references/doc-chain.md` の「検討資料 → DesignDoc」行（事業・製品の判断なら「検討資料 → Brief」行）を見て、採用方針・却下案と理由・未決事項が具体的に書かれているか確認する。欠けは未決事項に落とす。既存資料のレビューを頼まれたときはこの確認だけを回す
- **読者パス**（`/dev-docs:tech-writing` の3パスに加えて必ず回す）: ①先頭2画面に、読者が既に知っている情報や調査の規模が出ていないか ②見出しだけを順に読んで、誰が何をどの選択肢から決めるのか分かるか ③図が1枚以上あり、各セルに出所があるか ④比較表の列名・記号・評価段階に定義があるか。1つでも欠けたら構成を直す
- ユーザーの指摘がこのスキルの手順や観点の不備に起因するなら、`skill-improve` スキルに従って記録する（`skill: "dev-docs:tech-research-doc"`）

## 資料の標準構成

```markdown
# <テーマ>検討資料
- 作成日 / ステータス（検討中・決定済み等）

## この資料について
誰が何を決めるための資料か。選択肢は何件か。判断の前提条件（期限・許容コスト・評価の時間軸・やらない領域）。
**4〜6行。経緯の積み上げではなく、判断の枠を渡す節**

## 選択肢と推し
| 選択肢 | 概要 | 推奨 |
推し案とその理由を先頭文に置く。読者が最初に必要とするのはここ

## 比較（図または表）
全選択肢 × 判断を分けた観点のマトリクス。1枚で全体像が取れる形にする。
**列名・記号・評価段階の定義をこの節内に置く**

## 観点の定義
| 観点 | 何を評価するか | なぜ重要か |

## 各案の詳細
### <案の名前>
一行説明 → 調査事実（出典付き）→ 評価表 → 制約
### 除外した案: <名前>（理由付き）

## 次の一手
推しを選んだ場合に最初にやること。費用と期間を書く

## 未決事項
| 論点 | 推し | 判断者 |

## 付録
調査の規模（候補件数・ラウンド数・期間）、手法、手前で落とした案の一覧、出典。
**読者の判断材料でない情報はすべてここ**
```

構成は絶対ではない。ただし次の4点は崩さない。

- **読者が決めることと選択肢が冒頭にある**（判断ゲート・未決事項を末尾だけに置かない）
- **観点の定義が事実より先**
- **案別整理**（観点別に事実を並べない）
- **調査の過程は付録**

技術選定では「この資料について」に機能要件（必須 / 将来 / 前提条件）を置き、「選択肢と推し」を §6 相当の位置に下げてよい。読者が選定の当事者（開発メンバー）で、要件の共有が判断の前提になるため。読者が判断だけを下す立場（経営者・PdM・顧客）なら上の順のまま使う。

## 表現ルール

文章の書き方（結論先行・冗長表現の削除・箇条書きの規律など）は `/dev-docs:tech-writing` スキルに従う。以下は検討資料に固有のルール。

### 見出しは名詞句、主張は節の先頭文

見出しには、読者がその節で得るものを名詞句で書く（「選択肢と推し」「各案の詳細」「次の一手」）。主張を文の形のまま見出しにしない。

| 悪い見出し | 直し方 |
|---|---|
| `推奨は案 B です。ただし前提条件付きです` | 見出しは `選択肢と推し`。この文は節の**先頭文**に置く |
| `推し` `次点` `却下`（ランク名だけ） | 節見出しにしない。案のラベルとして各案に付ける |

理由は2つ。見出しだけを拾って資料の骨格を把握できること。主張は本文で根拠と一緒に読まれるべきで、見出しに置くと根拠のない断定として目に入ることだ。

### 前提は「判断の枠」であって経緯ではない

冒頭の「この資料について」は結論先行の例外ではない。読者が判断を下すための枠（誰が・何を・どの選択肢から・何を前提に）を4〜6行で渡す節であり、調査の経緯・背景の積み上げを書く場所ではない。**背景を3段落積んでから本題に入るのは逆茂木型で、`/dev-docs:tech-writing` が禁じている。** この節の直後に推し案が来る。

### 読者が初めて見る語には定義を付ける

比較表の列名、評価の記号、A/B/C のような段階、独自に作った観点名は、**その場で 1 行の定義を付ける**。書き手には自明でも、読者はその語を初めて見る。

| 悪い例 | 直し方 |
|---|---|
| 列名「運用負荷」だけを置く | 「**運用負荷**: 定常運用に要する作業量。A/B/C の 3 段」を凡例に書く |
| 「● / ◐ / ○」の意味を書かない | 列ごとに何が ● なのかを書く。列で基準が違うなら列ごとに分けて書く |
| 内部の用語（等級コード、軸の番号）をそのまま使う | 読者が追える言葉に言い換えるか、定義を添える |

**判定**: 資料を初見の読者として読み、定義なしに意味が取れない語が 1 つでもあれば直す。**前提ファイルや社内資料に定義があることは、資料に書いたことにならない。**

### 図を1枚以上入れる

文字だけの資料は構造が頭に入らない。次のどちらかは必ず入れる。

- **比較マトリクス**: 全選択肢 × 判断を分けた観点。`●`（強い）/ `◐`（条件付き）/ `○`（弱い）など3段で、1枚で全体像が取れる形にする
- **流れ図**: 次の一手が分岐を含むとき（「検証して、取れたら作る / 取れなければ戻る」）。Markdown なら mermaid、HTML なら `<pre class="mermaid">` で描ける

**図のセルも事実に出所を要求される。** 根拠を示せないセルは埋めず「未確認」と置く。図だから曖昧でよい、ということはない。

調査の規模を示す図（候補 N 件 → M 件のようなファネル）は作らない。読者の判断材料ではないため。

### コード参照を使わない

R1・T3 のような採番コードで要件や観点を参照しない。一覧表に # 列も作らない。読者がコードを見るたびに定義表へ戻る往復が発生するため。要件・観点は常に短い名称（「最小権限」「スケール性」）で呼び、文書全体で同じ語を使う。

### 評価は「全アプローチ共通の行順の評価表」で示す

メリット/デメリットの列挙は使わない。アプローチごとに同じ行順の評価表を置く:

```markdown
| 観点 | 評価 | 内容 |
|---|---|---|
| 検索性能 | ◎ | 全文検索を追加設定なしで使える |
| 最小権限 | ◎ | 閲覧権限をプロジェクト単位で分けられる。構成で充足 |
| データ分離 | △ | アプリ側の対策で担保する（別節の対策を必須とする） |
| 費用 | ◎ | 無料 |
```

行の並びが全アプローチで同じなら、読者は行位置だけで直接比較できる。凡例（◎ 強み / ○ 満たせる / △ 条件付き・実装でカバー / × 満たせない・重い制約）を最初に示す。横断比較サマリも同じ行順に揃える。

### 箇条書きに観点を付けるときは行頭プレフィックス

「取り込み量の上限がプロジェクトごとに独立（スケール性）」のような末尾ラベルではなく、「**スケール性**: 取り込み量の上限がプロジェクトごとに独立」と観点名を行頭に置く。

### 制約（動かせない条件）を独立して明示する

メリデメ・評価に加えて、**制約 = ハードリミットや外部条件として動かせないもの**を独立した表にする（| 制約 | 内容 | 影響 |）。「保存期間に上限がある」「利用できるリージョンが限られる」「1 日あたりの取り込み量に上限がある」のような、工夫で回避できない条件が意思決定では最も重い。デメリット（重いが対処可能）と混ぜない。

### 事実には出典、評価には理由

- 調査事実の直後に `（出典: [名前](URL)）` を付ける。公式ドキュメント > 公式ブログ > 信頼できるサードパーティの順で優先し、文末の出典一覧でも公式/その他を分ける
- 各事実セクションは**評価まで書き切る**。数値を並べて終わらず、「結論: この観点はどの方式でも決め手にならない」まで書く

## アンチパターン

| アンチパターン | なぜダメか | 代わりに |
|---|---|---|
| 調査の過程を成果として出す | 読者が欲しいのは選択肢と推しであって、何件調べたか・どう絞ったかではない | 本体は選択肢・推し・次の一手。過程は付録 |
| 判断ゲート・未決事項を末尾だけに置く | 読者が「何を決めるのか」を最後まで知れない。読む動機も組み立てられない | 冒頭の「この資料について」と「選択肢と推し」で先に示す |
| 文の形の見出し | 見出しを拾っても骨格が分からず、根拠のない断定が目に入る | 見出しは名詞句。主張は節の先頭文 |
| 独自の観点名・記号を定義せずに使う | 読者は語の意味を推測しながら読むことになり、比較表が読めない | 列名・記号・段階に 1 行の定義を付ける |
| 図が1枚もない | 選択肢が4件以上あると文字だけでは比較の全体像が取れない | 比較マトリクスか流れ図を入れる |
| 結論だけの ADR | チームは過程で妥当性を判断する。再検討時に同じ調査をやり直すことになる | 却下案・検証 Q&A・出典を残す |
| 観点別に事実を並べる構成 | 読者は「この方式を採るとどうなるか」を知りたいのに、方式像が頭の中で組み立て直しになる | アプローチ別に整理し、観点は評価表の行にする |
| 唐突な調査事実 | 「なぜこれを調べたのか」がないと読者は重要度を判断できない | 観点の定義を先に置き、事実は観点への答えとして出す |
| コード参照（R1/T3） | 定義表との往復を強いる | 名称で参照する |
| メリデメの箇条書き比較 | アプローチ間で項目の並びが揃わず、比較に頭を使わせる | 共通行順の評価表 |
| 「〜だろう」で書かれた数値・仕様 | 資料の信頼性が一点の誤りで崩れる | 出典を取る。取れなければ「要確認」と書く |
