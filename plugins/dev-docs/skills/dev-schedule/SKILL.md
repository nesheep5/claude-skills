# 開発スケジュール — いつ何を出すか

PRD の要求をどの順で・どれだけの期間で出すかを、エンジニアと PdM が合意するための文書。見積の精度より、**フェーズの切り方の根拠**と**見積が崩れる条件**が書かれていることを優先する。

## 進め方

1. **取り込み**: `${CLAUDE_PLUGIN_ROOT}/references/source-intake.md` に従い PRD と DesignDoc を得る。PRD の機能要件（優先度付き）と DesignDoc のコンポーネント分割・依存関係が無い場合は、それが無いとフェーズを切れないことを伝え、前提質問で最低限を補う
2. **前提質問**: 下の一覧から、決まっていないものを1問ずつ聞く。**見積の粒度**は必ず聞く
3. **執筆**: 下の構成で書く。`/dev-docs:tech-writing` の原則に従う
4. **下流チェック**: この文書は連鎖の末端なので、代わりに上流との整合を確認する。PRD の Must 要求がすべてどこかのフェーズに含まれているか、DesignDoc の依存関係とフェーズ順が矛盾していないか。矛盾は「未決事項」に落とす。**既存スケジュールのレビューを頼まれたときはこの段階だけ回す**
5. **自己レビュー**: `/dev-docs:tech-writing` の3パス
6. **フィードバック**: ユーザーの指摘がスキルの不備なら `skill-improve` スキルに従って記録する（`skill: "dev-docs:dev-schedule"`）

## 前提質問

- 見積の粒度はどれか: 人日の積み上げ / スプリント（N週）単位 / 月単位。粒度に合わせてフェーズ一覧の「期間」列の単位を決める
- 人員は何人か。並行で抱えている他タスクはあるか
- 固定の期日（契約・イベント・法規制の施行日）はあるか
- 最初に価値を出したい要求はどれか（PRD の Must の中でも順序があるか）
- 技術的に不確実で早めに検証したい部分はあるか（DesignDoc の未決事項から拾う）
- 外部依存（ストア審査・他チームの API・データ提供）とそのリードタイム

## 構成

```markdown
# <機能名> 開発スケジュール
- 作成日 / 作成者 / ステータス
- 関連文書: PRD / DesignDoc
- 見積の粒度: <人日 / スプリント / 月>

## フェーズ分割の方針
なぜこの切り方か。1段落（例: 「不確実性の高い外部連携を第1フェーズで検証し、UI は後回しにする」）

## フェーズ一覧
| フェーズ | 含める要求（PRD の要求名） | 完了条件 | 期間 | 依存 |
完了条件は確認できる状態で書く。依存は他フェーズ・外部要因

## マイルストーン
| 時期 | 状態 |
「その時点で成立している状態」を書く。日付が決められなければ相対（開始から N 週）。mermaid gantt は任意

## 見積の前提とリスク
人員・並行タスク・外部依存。「この前提が崩れると N 週延びる」の形で、見積が崩れる条件を列挙する

## 未決事項
| 論点 | 推し | 判断者 |
```

## 各節の要点

- **フェーズ分割の方針**: 「段階的に」だけでは方針ではない。早期価値 / リスク先取り / 依存解消 のどれを優先したかを書く
- **フェーズ一覧**: 要求名は PRD と同じ語を使う。1フェーズに Must を詰め込みすぎていないか（後半フェーズが Could だけなら、前半が重すぎる）
- **見積の前提とリスク**: 見積の数字より重要。前提が書かれていない数字は、崩れたときに誰も気づけない
- **期間**: 人日で積み上げる場合はバッファを別行で明示する。粒度が粗い場合は幅（2〜3スプリント）で書いてよい
