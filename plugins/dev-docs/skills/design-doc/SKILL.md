# DesignDoc — どう作るか

DesignDoc は PRD の要件をどう実装するかを、エンジニア間および PdM と合意するための文書。設計の正しさより「なぜこの設計にしたか」が追えることを優先する。読者は実装するエンジニア（詳細を知りたい）と PdM（要件が満たされるか・トレードオフは何かを知りたい）の両方。

## 進め方

1. **取り込み**: `${CLAUDE_PLUGIN_ROOT}/references/source-intake.md` に従い PRD を得る。技術調査資料があればそれも得る。PRD が無ければ「関連文書: PRD なし」と書き、PRD の引き渡し情報（優先度付き機能要件・非機能要件・制約・受け入れ条件）を前提質問で補う
2. **前提質問**: 下の一覧から、PRD と調査資料で決まっていないものを1問ずつ聞く。設計対象のコードベースが手元にあれば、質問の前に現状を読む
3. **執筆**: 下の構成で書く。`/dev-docs:tech-writing` の原則に従う。複数案の比較が必要になったら `/dev-docs:tech-research-doc` の評価表の形式（全案共通の行順）を使う
4. **下流チェック**: `${CLAUDE_PLUGIN_ROOT}/references/doc-chain.md` の「PRD + DesignDoc → 開発スケジュール」行を見て、コンポーネント分割と依存関係が具体的に書かれているか確認する。あわせて PRD の機能要件（Must）がすべてどこかのコンポーネントで扱われているか対応を確認し、扱われていない要求は「未決事項」に落とす。**既存 DesignDoc のレビューを頼まれたときはこの段階だけ回す**
5. **自己レビュー**: `/dev-docs:tech-writing` の3パス
6. **フィードバック**: ユーザーの指摘がスキルの不備なら `skill-improve` スキルに従って記録する（`skill: "dev-docs:design-doc"`）

## 前提質問

- 既存システムのどこに手を入れるか。触ってはいけない部分はあるか
- 設計を縛る非機能要件はどれか（PRD の目標値のうち、設計で最も効くもの）
- データの所有者と保持期間。既存データの移行は要るか
- 外部サービス・他チームとの境界（API・イベント・バッチ）はどこか
- リリース方法（一括 / 段階 / フラグ）に制約はあるか
- 却下済みの案はあるか（あれば理由ごと「検討した代替案」に載せる）

## 構成

```markdown
# <機能名> DesignDoc
- 作成日 / 作成者 / ステータス（草案・レビュー中・合意済み）
- 関連文書: PRD / 技術調査資料 / 開発スケジュール（あれば）

## 概要と目的
何を作るか、PRD のどの要求に応えるかを3〜5文。PdM が読むのはここまでを想定して書く

## 現状と課題
既存システムの現状（構成・データ・制約）と、要件を満たすために変えなければならない点

## 設計方針
設計判断の軸を2〜4個。「なぜこの方針か」を要件・制約に接続する（例: 「非機能要件の p95 500ms を満たすため、集計は事前計算に寄せる」）

## アーキテクチャ
コンポーネント構成図（mermaid）。既存と新規を区別する

## コンポーネント設計
コンポーネントごとに: 責務 / インターフェース / 依存先。PRD の要求名との対応を明示する

## データ・API
スキーマ変更・API 仕様・イベント定義。移行が要るデータは移行方法まで

## 検討した代替案
| 案 | 概要 | 採らなかった理由 |
技術調査資料があればリンクし、結論を引用する

## 非機能・運用・移行
PRD の非機能要件の各観点に、設計でどう応えるか。監視・障害時の挙動・ロールバック・段階リリース

## テスト方針
どの層で何を検証するか。受け入れ条件との対応

## 未決事項
| 論点 | 推し | 判断者 |
```

## 各節の要点

- **設計方針**: DesignDoc の中核。ここが「拡張性を考慮する」のような一般論なら書き直す。方針は要件か制約から導かれていなければならない
- **コンポーネント設計**: PRD の Must 要求がすべてどこかのコンポーネントに紐づく。紐づかない要求は下流チェックで検出する
- **検討した代替案**: 技術調査資料が無ければ「調査未実施」と書く（doc-chain.md の扱いと同じ）。空にしない。「他に案が無かった」なら「単一案。理由: 〜」と書く。却下理由が残っていないと、レビューで同じ案を蒸し返される
- **非機能・運用・移行**: PRD の非機能要件の表と同じ行順で応える。設計で満たせない目標値は隠さず未決事項に載せる
- **図**: mermaid で書く。Confluence 等に貼る場合は、`mermaid-to-image` スキルがあればそれで画像化する（無ければ mermaid のまま渡し、貼り付け先での描画をユーザーに任せる）
