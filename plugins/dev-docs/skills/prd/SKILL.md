# PRD — 何を提供するか

PRD はユーザーに提供する機能の要件を、PdM とエンジニアが合意するための文書。DesignDoc の直接のインプットであり、ここで機能要件の優先度と非機能要件の目標値が無いと、エンジニアは設計判断ができない。

## 進め方

1. **取り込み**: `${CLAUDE_PLUGIN_ROOT}/references/source-intake.md` に従い Brief を得る。Brief が無ければ「関連文書: Brief なし」と書き、Brief の引き渡し情報（課題・対象ユーザー・成功指標・やらないこと）を前提質問で補う
2. **前提質問**: 下の一覧から、Brief で決まっていないものを1問ずつ聞く
3. **執筆**: 下の構成で書く。`/dev-docs:tech-writing` の原則に従う
4. **下流チェック**: `${CLAUDE_PLUGIN_ROOT}/references/doc-chain.md` の「PRD → DesignDoc」「PRD + DesignDoc → 開発スケジュール」行を見て、引き渡し情報が具体的に書かれているか確認する。欠けは「未決事項」に落とす。**既存 PRD のレビューを頼まれたときはこの段階だけ回し、「どの節に何が無く、DesignDoc のどこが書けなくなるか」を伝える**
5. **自己レビュー**: `/dev-docs:tech-writing` の3パス
6. **フィードバック**: ユーザーの指摘がスキルの不備なら `skill-improve` スキルに従って記録する（`skill: "dev-docs:prd"`）

## 前提質問

- 機能を使う主体は誰か。複数いるなら権限や役割の違いはあるか
- 機能を使う前後でユーザーの行動はどう変わるか（ユーザーストーリーの材料）
- 要件のうち、無いとリリースできないもの（Must）と、後回しにできるもの（Should / Could）はどれか
- 性能・可用性・データ量の期待値。「今の画面と同じくらい」のような相対表現でも良いので基準を得る
- 既存機能・外部サービス・法規制・契約による制約はあるか
- 「完成した」をどう確認するか（受け入れ条件の材料）

## 構成

```markdown
# <機能名> PRD
- 作成日 / 作成者 / ステータス
- 関連文書: Brief / DesignDoc / 開発スケジュール（あれば）

## 概要
何を誰に提供するか。Brief の課題と成功指標を2〜3文で引用する（Brief が無ければここで仮置きする）

## ユーザーストーリー
「<誰>は<状況>で<何をしたい>。なぜなら<目的>」の形で列挙する。優先度順

## 機能要件
| 要求名 | 優先度 | 内容 |
優先度は Must / Should / Could。要求名は短い名称で、以降の文書でも同じ名称で参照する（R1 のような採番コードは使わない）

## 非機能要件
| 観点 | 目標値 | 根拠 |
観点: 性能 / 可用性 / セキュリティ・権限 / データ保持 / 監査・ログ。目標値は数値。決められないものは「未定（判断者: 〜）」

## 制約・前提
既存システム・外部サービス・法規制・契約・期限。動かせない条件を明示する

## 受け入れ条件
機能要件ごとに「〜のとき〜となる」の形で、確認できる条件を書く

## スコープ外
今回やらないこと。Brief の「やらないこと」を引き継ぎ、PRD で新たに除外したものを追加する

## 未決事項
| 論点 | 推し | 判断者 |
```

## 各節の要点

- **機能要件**: 「〜できる」で終わる1行が1要求。UI の細部（ボタンの色・配置）は書かない。Must が全体の半分を超えたら優先度付けが機能していないので問い直す
- **非機能要件**: エンジニアが設計で最も困る節。「高速に」「安全に」は欠けとみなす。数値が無ければ相対基準（「既存の一覧画面と同等」）を書き、判断者を付けて未決事項に載せる
- **受け入れ条件**: テストケースの元になる。機能要件の各行に最低1つ対応させる
- **要求名の一貫性**: 機能要件の要求名は、DesignDoc・スケジュールでも同じ語で使う。ここで決めた名称が下流の集計キーになる
