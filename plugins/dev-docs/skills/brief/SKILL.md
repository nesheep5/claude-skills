# Brief — なぜやるか

Brief は「この施策をなぜやるのか」に PdM とエンジニアが合意するための文書。PRD の上流であり、ここで課題と成功指標が曖昧だと PRD 以降の全文書がぶれる。

## 進め方

1. **取り込み**: Brief は最上流なので上流文書は無い。既存の議事録・チケット・Slack の要約があれば受け取り、関連文書の欄に出所を書く
2. **前提質問**: 下の一覧から、答えが決まっていないものを1問ずつ聞く
3. **執筆**: 下の構成で書く。`/dev-docs:tech-writing` の原則に従う
4. **下流チェック**: `${CLAUDE_PLUGIN_ROOT}/references/doc-chain.md` の「Brief → PRD」行を見て、引き渡し情報が具体的に書かれているか確認する。欠けは「未決事項」に落とす。**既存 Brief のレビューを頼まれたときはこの段階だけ回す**
5. **自己レビュー**: `/dev-docs:tech-writing` の3パス（構成 / 冗長 / AI臭）
6. **フィードバック**: ユーザーの指摘がスキルの不備なら `skill-improve` スキルに従って記録する（`skill: "dev-docs:brief"`）

## 前提質問

- 今、誰がどんな場面で困っているか。困っていることを示す事実（問い合わせ件数・離脱率・工数）はあるか
- この施策をやらないと何が起きるか
- 成功したと言える状態は何か。数値で言えるか（言えないなら「計測方法が未定」と書く）
- 意図的にやらないことは何か
- 期限や外部要因（契約・法規制・他チームのリリース）はあるか

## 構成

```markdown
# <施策名> Brief
- 作成日 / 作成者 / ステータス（草案・レビュー中・合意済み）
- 関連文書: PRD（あれば）

## 背景と課題
誰が・どんな場面で・何に困っているか。困っている事実を数値や具体例で示す。1〜3段落

## 対象ユーザー
誰のための施策か。ペルソナ名ではなく、行動や状況で定義する（「週1回以上レポートを出力する管理者」）

## 目指す状態と成功指標
施策後にどうなっているか。指標は「何を・いつまでに・どれだけ」。計測方法が未定なら未定と書く

## やらないこと
この施策で意図的に扱わない範囲。理由を1行添える

## 未決事項
| 論点 | 推し | 判断者 |
```

## 各節の要点

- **背景と課題**: 解決策を書かない。「〜機能が無い」は課題ではなく解決策の裏返しなので、「〜できないために何が起きているか」まで戻す
- **成功指標**: 「利便性向上」のような計測できない表現は欠けとみなす。数値が出せないなら代替指標（定性調査の実施等）を書く
- **やらないこと**: PRD でスコープ論争が起きるのを防ぐ節。空にしない
