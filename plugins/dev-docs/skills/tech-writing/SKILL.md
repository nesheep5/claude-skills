# 技術文書の文章術

良い技術文書の条件は2つ。結論と根拠が読む順に現れること（構成）と、削って意味が変わらない語がないこと（文）。このスキルは執筆時に従う原則と、書き終えた後に必ず回す自己レビューパスを定める。

## 構成の原則

### 結論先行

文書全体・セクション・段落の3レベルすべてで「答え → 理由 → 詳細」の順に書く。結論を先に知った読者は理由を「検証」として読めるが、結論が最後だと理由を「暗記」しながら読むことになる。

Before:
> 現在の実装では API 呼び出しごとに認証トークンを再取得している。トークン取得には平均 300ms かかり、一覧画面では 20 回の API 呼び出しが発生する。そのため、トークンキャッシュを導入したい。

After:
> トークンキャッシュを導入したい。現在は API 呼び出しごとにトークンを再取得しており（平均 300ms）、20 回呼び出す一覧画面では合計 6 秒の無駄が生じているためだ。

### トピックセンテンス

各段落の先頭文に、その段落の主張を置く。先頭文だけを拾い読みして文書の論旨が通るのが完成形。先頭文が「ところで」「なお」で始まる段落は、構成を見直すサイン。

Before:
> なお、バッチ処理は毎晩 1 時に起動する。実行時間は平均 30 分で、週末は 70 分まで伸びる。次回のリリースで集計処理を追加する予定もある。このままでは朝 5 時の締め切りに間に合わなくなる。

After:
> バッチ処理は朝 5 時の締め切りに間に合わなくなる。毎晩 1 時起動で実行時間は平均 30 分、週末は 70 分に伸びる。ここに次回リリースの集計処理が加わるためだ。

### 逆茂木型の禁止

前提・背景・経緯を積み上げてから本題に入る構成（木下是雄『理科系の作文技術』の言う逆茂木型）を避ける。背景説明が本題より先に3段落以上続いたら、本題を先頭に出し、背景は「なぜなら」の位置に移す。

Before:
> 以前、通知基盤を刷新した。その際、外部ライブラリの都合で言語ランタイムを旧版に固定した。その後ライブラリが新版に対応し、固定の理由は消えた。ランタイムを新版へ上げたい。

After:
> ランタイムを新版へ上げたい。旧版に固定していたのは通知ライブラリが未対応だったためだが、その制約は解消した。

### セクション間の接続

各セクションの末尾または次セクションの冒頭で、「なぜ次を読むのか」を1文で動機づける。見出しだけで話題が飛ぶと、読者はセクションごとに文書の目的を推測し直すことになる。

Before:
> ## 現状の課題
> 検索 API のレスポンスが p95 で 1.8 秒かかっている。
>
> ## インデックス設計

After:
> ## 現状の課題
> 検索 API のレスポンスが p95 で 1.8 秒かかっている。遅延の大半はインデックス未整備によるフルスキャンなので、まずインデックス設計から検討する。
>
> ## インデックス設計

### 文書の目的を1つに絞る

説明（なぜこうなっているか）・手順（どうやるか）・参照情報（一覧・仕様）は読まれ方が違う。1つの文書に混ぜない。混在しそうなら文書を分割するか、参照情報を付録に隔離する。

Before:
> ## デプロイ手順
> 1. `bin/deploy staging` を実行する
> 2. なお、staging と production を分けているのは、マイグレーションの巻き戻しコストを抑えるためである。以前、本番で……
> 3. ヘルスチェックが緑になったら `bin/deploy production` を実行する

After:
> ## デプロイ手順
> 1. `bin/deploy staging` を実行する
> 2. ヘルスチェックが緑になったら `bin/deploy production` を実行する
>
> 環境を分けた理由は [ADR「デプロイ環境の分離」](./adr-deploy-environments.md) に書いた。

## 文の原則

### 一文一義

1文には1つの主張だけを入れる。「〜であり、〜だが、〜なので」と接続助詞でつながった文は分割する。60字を超えた文は分割を検討する。

Before:
> 現行の同期処理は実装が単純で運用実績もあるが、件数が 1 万を超えるとタイムアウトするので、非同期化してジョブキューに逃がす案を検討している。

After:
> 現行の同期処理は件数が 1 万を超えるとタイムアウトする。実装の単純さと運用実績は利点だが、この上限は許容できない。非同期化してジョブキューに逃がす案を検討している。

### 能動態優先

「〜される」「〜と考えられる」より「〜する」「〜と考える」。主語のない受動態は、誰がやるのかを読者に推測させる。

### 無駄な語の削除

削って意味が変わらない語は削る。頻出の圧縮パターン:

| 冗長 | 簡潔 |
|---|---|
| 〜することができます | 〜できる |
| 〜を行います | 〜します |
| 〜という形になっています | 〜になっている |
| 〜する必要があります | 〜が必要だ |
| 〜だと考えられます | 〜だ（根拠があるなら断定する） |
| まず最初に | まず |
| 〜について説明します | （見出しに任せて削る） |

### 用語の一貫性

同じ概念は文書全体で同じ語で呼ぶ。「利用者 / ユーザー / エンドユーザー」が混在すると、読者は「別物か？」という無駄な問いを抱える。言い換えの豊かさ（elegant variation）は技術文書では欠点になる。

### 事実と意見の書き分け

事実は断定で書き、意見は意見と分かる形（「〜と判断した」「〜を推す」）で書く。事実の記述に「〜のはずです」「おそらく」を混ぜない。

Before:
> 現行の全文検索は性能が悪いのでおそらく専用の検索エンジンに移行すべきです。

After:
> 現行の全文検索は、想定するデータ量で p95 が 2 秒を超える（負荷試験の結果）。目標の 500ms を満たさないため、専用の検索エンジンへの移行を推す。

### 根拠の併記（調査系ドキュメント）

調査結果をもとに意思決定する文書では、数値・上限・仕様などの調査事実に出典（URL）を併記する。出典が取れない事実は「要確認」と明記する。

### 箇条書きの規律

論理の流れ（AだからB、しかしC）は散文で書く。箇条書きは並列な列挙にのみ使い、ネストは2段まで。箇条書きの各項目が「〜のため」「しかし〜」で始まっていたら、それは散文で書くべき論理展開。

Before:
> - インメモリの KVS はレイテンシが低いため第一候補になる
> - しかし永続化の設定が運用コストを押し上げる
> - そのため今回は既存 DB のキャッシュテーブルを採用する

After:
> インメモリの KVS はレイテンシが低く第一候補だったが、永続化設定の運用コストが見合わない。今回は既存 DB のキャッシュテーブルを採用する。

## AI臭アンチパターン

| アンチパターン | 例 | 直し方 |
|---|---|---|
| 同内容の反復 | 本文で述べたことを「まとめ」で言い換えて繰り返す | まとめは削るか、本文にない判断・次アクションだけを書く |
| 空疎な前置き | 「重要なのは」「注目すべき点として」 | 前置きを削り、中身から書き始める |
| 過剰なヘッジ | 「一般的には〜と言われています」「〜かもしれません」の乱用 | 根拠を確認して断定するか、「未確認」と明記する |
| 中身のない総括 | 「適切に設計することが重要です」 | 何をどうするのが適切かの具体を書く。書けないなら削る |
| 過剰な強調 | 太字の乱発・絵文字・「非常に」「極めて」 | 強調は1セクション1箇所まで。程度副詞は数値に置き換える |
| 箇条書きの乱用 | 3行の散文で書ける説明を5項目のリストに分解 | 論理の流れは散文に戻す |

## 自己レビューパス（書き終えたら必ず回す）

1. **構成パス**: 各段落の先頭文だけを抜き出して読む。それだけで論旨が通らなければ、段落の順序か先頭文を直す
2. **冗長パス**: 全文を読み、削って意味が変わらない語・文・段落を削る。圧縮パターン表と照合する
3. **AI臭パス**: アンチパターン表と照合し、該当箇所を書き直す
