# dev-docs

開発にまつわる文書の作成・修正・レビューを、1 つのスキル（`/dev-docs:doc`）で支援するプラグイン。書く前に読者と目次を利用者と合意し、プラグインの共通ルールに、利用者やプロジェクトのローカルルールを重ねて書く。セッション中に受けた書き方の指摘はローカルルールに取り込まれ、使うほど好みに沿った文書が出るようになる。

## 文書は読者と目次の合意から書き始める

dev-docs は次の考え方で作っている。それぞれ、何をするかと、なぜそうするかを並べる。

- **書く前に、読者・答える問い・目次・用語を合意する。** 種別ごとの決まった構成は、その文書の議論の筋に合わないことがある。書いてから構成を直すより、目次の段階で直す方が安い
- **結論を先に置き、概要から詳細へ分解する。** 冒頭の数行だけで、読者が判断に要ることを受け取れるようにする。背景を積み上げてから本題に入る構成や、後半を読まないと前半が分からない構成を避ける
- **見出しはメッセージ型にする。** 見出しにその節の結論を短い文で書き、見出しだけを上から読めば論旨がたどれるようにする。「はじめに」「〜とは？」「まとめ」のようなブログ調の見出しは使わない
- **そのドメインで使われている語を使う。** 比喩や気の利いた言い換え、独自の造語は使わない。新しい語が要るときは、合意してから使う
- **ID を振って ID で参照しない。** 簡潔に書ける反面、読者は ID を見るたびに定義へ戻ることになる。要件や論点は短い名前で呼び続ける
- **一次情報に当たり、出典を付ける。** 読者が記載の正当性を後から自分で確かめられるようにする。種別を問わず、調べた事実を含む文書すべてに当てる
- **調査と資料作成を分ける。** 調べた結果は文書とは別の調査記録に持ち、文書はそこから書き起こす。表現の修正を重ねても、調査内容が薄まらないようにするため
- **ビジネス文書と論文の作法を取り入れる。** ビジネス文書からはピラミッド構造と冒頭の要約を、論文からは問いの明示・事実と解釈の区別・限界の明記を取り入れている

規則の正本は `references/writing.md`（共通ルール）にある。

## 依頼の種類で、回す段階が変わる

インストールは次の 1 行（Claude Code 2.1.275 以降）。

```
/plugin install dev-docs --marketplace nesheep5/claude-skills
```

`/dev-docs:doc` で明示して呼べる。明示しなくても、文書の作成・修正・レビューの依頼で呼ばれる。

流れは 6 段階ある。

1. 依頼を見極める: 新規作成 / 大きな改稿 / 小さな修正 / レビュー、表現だけの修正か中身の修正か、文書の種別を判定し、ローカルルールを読む
2. 調べる: 調べることがあるときだけ。結果は調査記録に書く
3. 合意する: 読者と目的・答える問い・目次・用語を示し、了承を得る
4. 書く: 調査記録から書き起こす
5. 自己レビューする: 見出しだけで論旨が通るか、冒頭で判断に要ることが分かるか、用語・参照・出典、調査記録との突き合わせ
6. 下流チェック: 次の文書（PRD → DesignDoc など）に渡す情報がそろっているか

依頼の種類ごとに回す段階:

- 新規作成・大きな改稿: すべて
- 小さな修正: 合意を省く。表現だけの修正なら調べ直さず、調査記録にも触れない
- レビュー: 自己レビューと下流チェックだけを回し、指摘を返す

## 7 つの種別に固有の知識を持つ

種別ごとの reference（`references/types/`）は、その種別に必須の情報・たたき台の目次・下流に渡すものを持つ。たたき台の目次は出発点で、合意フェーズで文書ごとに組み替える。

- Brief（`brief`）: なぜやるか
- PRD（`prd`）: 何を提供するか
- DesignDoc（`design-doc`）: どう作るか
- 開発スケジュール（`dev-schedule`）: いつ何を出すか
- 検討資料（`research`）: 調査をもとに何を選ぶか。案を比べる型と、事実 → 要件 → ギャップの型を持つ
- 打ち合わせ資料（`meeting`）: 打ち合わせで何を決め、何を聞くか
- 依頼書（`request`）: 誰に何をどの状態まで頼むか

どの種別にも当たらない文書（README・ADR・手順書など）は、共通ルールと合意フェーズだけで書く。種別ごとの書き方は、使いながら育てていく。

## 出力先は、指定 → 既存 → ローカルルール → 慣習 → 既定の順で決まる

1. 依頼で示された場所
2. 既存の文書の修正なら、その文書の場所
3. ローカルルール（`style.md`）で指定した置き場
4. プロジェクトの慣習（`docs/` の下に同じ種別の文書があるなど）
5. どれにも当たらなければ `docs/<種別>/YYYY-MM-DD-<テーマ>.md`

調査記録は、文書の隣に `<文書名>.research.md` で置く。ツール専用の隠しディレクトリやリポジトリの外は既定にしない。人に読ませる文書なので、見つけやすく、共有・レビューできる場所に置く。書いた場所は毎回返答で伝える。

## ローカルルールは差分だけを重ねる

プラグイン本体の上に、2 つのローカルを重ねる。重なったときは プロジェクト > 利用者 > プラグイン の順で優先する。

- **利用者のローカル**: プラグインの設定 `local_rules_dir` で指定するディレクトリ。有効化したときの設定ダイアログか `/config` で入れる。未設定なら、プラグインのデータディレクトリ（`~/.claude/plugins/data/<id>/`）を使う。こちらはアンインストールで消えるうえ、`~/.claude` の下にあるため書き込みのたびに許可を求められたり、非対話の実行では拒否されたりすることがある。指摘を自動で取り込みたいなら、`~/.claude` の外のディレクトリを設定する
- **プロジェクトのローカル**: プロジェクトのルートの `.claude/dev-docs/`。コミットしてチームで共有するものとして扱い、dev-docs は読むだけにする。書き込むのは、利用者に聞いて了承を得たときだけ

どちらにも次のファイルを置ける。

- `style.md`: 書き方の好み。文書や調査記録の置き場の指定もここに書く
- `glossary.md`: 用語集。利用者のローカルではプロジェクトごとの節に分かれる
- `templates/<種別>.md`: 会社やチームの文書テンプレート。見出しの構成と文言はそのまま使い、メッセージ型はその下の小見出しにだけ当てる
- `templates/<種別>.guide.md`: テンプレートの各見出しを埋めるための記載ルールと追加の前提質問
- `types/<種別>.md`: プラグインに無い種別の追加、またはプラグインの種別の上書き
- `promote-candidates.md`: プラグイン本体に昇格させたい一般則の候補（利用者のローカルだけ）

ローカルにスキルを丸ごと複製しない。複製すると正本が 2 つになり、どちらが効いているか追えなくなる。変えたいところだけを上のファイルに書く。

## 書き方の指摘は、ローカルルールに自動で取り込まれる

セッション中に書き方の指摘を受けると、dev-docs は文書を直すのと同時に、指摘を 4 つに振り分けて取り込む。

- この文書だけの話（「この節は削って」）: 取り込まない
- 利用者の好み（「ID を振らないで」）: 利用者のローカルの `style.md` に追記する
- ドメインの語（「その言い方ではなく『〜』と呼んでいる」）: 利用者のローカルの `glossary.md` の、プロジェクトの節に追記する。チームの用語集があれば、載せるかを聞く
- 誰にでも効く一般則: `promote-candidates.md` に追記する。プラグイン本体には自動で書き込まない

確認を挟まずに書き込み、返答の末尾に「好みに追加: 〜」のように 1 行で知らせる。取り違いなら「それは今回だけ」と言えば消える。既存の項目と矛盾するときは、書き込まずに聞く。

## 他のスキルとは役割で境界を引く

次は対象外にしている。

- 個人用ナレッジやメモへの記録
- 文の自然さ（語感・AI っぽさ）だけの手直し
- 社外向けの技術記事・ブログ。導入から入る読み物の構成が正当な文書で、dev-docs の規則と衝突するため

プラグイン本体は、他のスキルを名前で参照しない。公開しているプラグインから、利用者の手元にしかないスキルへの依存を作らないため。手元のスキルの側から dev-docs を名指しするのはよい（例: 個人用 wiki のスキルの説明に「他人に渡す資料は dev-docs を使う」と書く）。

## 0.2 から移行するときは、設定とテンプレートを移す

- 0.2 の 6 スキル（`brief` / `prd` / `design-doc` / `dev-schedule` / `tech-research-doc` / `tech-writing`）は `doc` 1 つにまとめた。旧スキルの名前での呼び出しはできない
- 設定 `org_templates_dir` は `local_rules_dir` に置き換えた。新しい設定にディレクトリを指定し、旧ディレクトリの `<種別>.md` と `<種別>.guide.md` をその下の `templates/` に移す
- `tech-research-doc` 向けのテンプレートは `templates/research.md` に名前を変える

## 保守

- 共通ルールの正本は `references/writing.md`。自己レビューのパス（`references/review.md`）は、その見出しの名前で参照している
- 種別を足すときは、`references/types/<種別>.md`、`references/doc-chain.md`、`skills/doc/SKILL.md` の種別の一覧、`skills/doc/evals/trigger.json` を同時に直す
- references の中の `${...}` は展開されない。展開されるのはスキル本文だけなので、ローカルの置き場の実際の値は SKILL.md の「置き場の解決」で渡している
- 評価ケースは `skills/doc/evals/`。`trigger.json` は発火（`query` と `should_trigger`）、`results.json` は振る舞い（`prompt` と `checks`）。description を変えたら発火を確かめ直す。例文に業務固有の語を入れない
- 形のテストは `bash tests/dev-docs.test.sh`
