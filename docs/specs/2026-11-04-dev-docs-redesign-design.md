# dev-docs 再設計

- 作成日: 2026-11-04
- ステータス: 草案（作者の承認待ち）
- 対象: `plugins/dev-docs/`

## 要約

dev-docs を「開発にまつわる文書の作成・修正・レビュー」を 1 つで受けるスキルに作り直す。書き始める前に、読者・答える問い・目次・用語を利用者と合意する。文書の種別ごとの知識は references に移し、利用者や会社の書き方はローカルルールとして差分だけを重ねる。セッション中に受けた書き方の指摘は、ローカルルールに自動で取り込む。

## なぜ作り直すか

資料作成を頼むと、ブログ調の構成やタイトルになり、後半を読まないと前半が分からない資料が出てくることが多い。使われ方を振り返ると、原因は 3 つあった。

- 呼ばれていない。資料作成の依頼で dev-docs が呼ばれないことが多かった。設計書やスケジュールのように依頼の語がはっきりしていれば呼ばれる。打ち合わせ用の資料・依頼書・メモと、既存資料の修正では、ほとんど呼ばれなかった。ブログ調の資料は、呼ばれなかったときに出ていた。個人用ナレッジを書く別のスキルが同じ依頼で呼ばれ、その書式が資料に流れ込むこともあった
- 呼ばれても、種別ごとに固定した構成が議論の筋に合わないことがある。検討資料のスキルで「案を比べる型」に沿って書いた資料に、「事実 → 考慮すべき要件 → 現状とのギャップの順なら議論しやすい」という直しが入った
- 規則が種別スキルに散らばっている。「見出しの書き方」「判断材料を冒頭に置く」「ID で参照しない」は検討資料や PRD のスキルにしかなく、他の文書には届かない

加えて、ローカルの調整をスキルの複製で行うと、正本が 2 つになり、どちらが効いているか追えなくなる。これは仕組みの側で防ぐ必要がある。

## 目標

- 開発にまつわる文書の作成・修正・レビューの依頼で、確実に呼ばれる
- 出てくる文書が、冒頭の数行で読者の判断に必要なことを渡し、概要から詳細へ分解する構成になる
- 見出しだけを上から読むと、文書全体の論旨がたどれる
- 文書に使う語が、そのドメインで使われている語（ユビキタス言語）と一致する
- 利用者の好みや会社のテンプレートを、プラグイン本体を書き換えずに重ねられる
- 使うほどに、利用者の好みに沿った文書が出るようになる

## やらないこと

- 種別ごとの書き方を、この再設計で作り込むこと。種別の reference は今のスキルの内容を移す程度にとどめ、使いながら育てる（作者の判断）
- 文の自然さ（語感・リズム・AI 臭さ）だけの手直し。それは文章の自然さを扱う別スキルに任せる。dev-docs は構成・論旨・用語を受け持つ
- 個人用ナレッジ（wiki・メモ帳）の書式。自分のための記録は対象外
- 社外向けの技術記事・ブログ。読み物として導入から入る構成が正当な文書で、失敗条件と衝突するため（私の判断）。README・ADR・手順書は開発の文書として受ける。開発の文書に対する「推敲して」「冗長さを削って」も受ける（構成と冗長さは dev-docs の担当。語感だけの手直しが別スキル）
- Confluence などの外部ツールへの直接書き込み

## 失敗とみなすもの

次のどれかに当たれば、手順どおり動いていても失敗とする。

- ブログ調の構成やタイトルが出る（「はじめに」「〜とは？」「まとめ」、疑問形・呼びかけ・比喩の見出し、結論が末尾）
- 要件や論点に ID を振り、本文で ID だけを使って参照する
- 文書のドメインに無い造語や、気の利いた言い換えが出る
- 小さな修正のたびに合意フェーズを挟み、利用者の手を煩わせる
- ローカルの情報（会社のテンプレート、用語、好み）が公開リポジトリに入る
- ローカルにスキルの複製ができ、正本が 2 つになる

## 前提と制約

- このリポジトリは公開されている。プラグイン本体には、会社名・社内の語彙・ローカルのパス・非公開プロジェクトの情報を入れない（リポジトリの `CLAUDE.md`）
- 変更後は `bash tests/validate.sh` と `bash tests/git-hooks.test.sh` を通す
- スキルの変更は、発火と結果の両方を評価してから完了とする
- 利用者は作者 1 人を主に想定するが、公開しているので他の利用者が入れても成り立つように書く
- 依存は「ローカル → dev-docs」の向きだけにする（作者の判断）。dev-docs は公開リポジトリなので、本体からローカルや他配布のスキルを名指しで参照しない。他スキルとの境界は「個人用ナレッジの記録」「文の自然さだけの手直し」のように役割で書く。ローカルのスキルが dev-docs を名指しするのはよい。旧版が参照していた別配布のスキル 2 つへの言及は外す

## 決めたこと

### スキルは 1 つにまとめる（作者の判断）

今の 6 スキル（brief / prd / design-doc / dev-schedule / tech-research-doc / tech-writing）を廃止し、1 つのスキルにする。呼ばれない原因の大半は「対応する種別スキルが無い資料」と「修正依頼」にあり、種別ごとの description では網羅できないため。

description は、開発にまつわる文書（設計書・要件・調査資料・打ち合わせ資料・依頼書など）の作成・修正・レビューを広く受ける。他人に渡す資料ならこのスキルを使い、個人用ナレッジの記録や文の自然さだけの手直しは対象外と、役割で書き分ける（他スキルの名前は出さない）。

これだけでは、個人用ナレッジを書くスキルが手元にある場合、そのスキルが同じ依頼を受けにいくのを防げない。そうしたスキルの側の description で「他人に渡す資料」を対象外にすると、競合が減る（任意。リポジトリの外の作業）。

### 流れ

1. **依頼の見極め**: 新規作成 / 大きな改稿 / 小さな修正 / レビューのどれかを判定する。小さな修正は、表現だけの修正か中身の修正かも見分ける。文書の種別を判定し、種別の reference とローカルルールを読む。種別に当たらない文書は、共通ルールだけで書く
2. **調査**（調べることがあるときだけ）: 結果を調査記録に書く（下の「調査記録」）
3. **合意フェーズ**（新規作成と大きな改稿のみ）: 次の 4 点を 1 つのメッセージで示し、利用者に直してもらう
   - 読者と、その人がこの文書で何を決める・何をするか
   - この文書が答える問い
   - 目次。メッセージ型の見出しに、その節で言うことを 1 行ずつ添える
   - 主要な用語。用語集・上流文書・コード・利用者の発話から取る。新しく名付ける語があれば、ここで提案する
4. **執筆**: 調査記録から書き起こす
5. **自己レビュー**: 見出しだけで論旨が通るか、冒頭の数行で判断に必要なことが分かるか、ID 参照・前方参照・造語が無いか、種別の必須情報がそろっているか、文書の事実が調査記録までたどれるか
6. **下流チェック**: 次の文書に渡す情報が具体的に書かれているか。今の `references/doc-chain.md` を引き継ぐ

既存文書のレビューでは 5 と 6 だけを回し、指摘を返す。小さな修正では 3 を省くが、直した箇所には同じ規則を当てる。

### 調査記録（作者の判断）

調査と資料作成を分ける。調査内容は合っているが表現を変えてほしい、という修正はよく起きる。そのたびに文書を書き直すと、言い回しと一緒に事実や出典が削られ、調査内容が薄まっていく。これを避けるため、調べた結果は文書とは別のファイル（調査記録）に持つ。

- 調査記録に書くもの: 事実と出典（確認日つき）、出典が取れなかったもの、そこから言える解釈。解釈は事実と分ける
- 文書は調査記録から書き起こす。文書に載せる事実は調査記録にあるものだけにし、文書の側で新しい事実を足さない
- 表現だけの修正では文書だけを直し、調査記録に触れない
- 中身を変える修正（調べ直し・事実の追加）では、先に調査記録を直してから文書に反映する
- 文書から事実を削るのは編集上の判断としてよい。調査記録からは消さない
- 自己レビューで調査記録と突き合わせる。文書の事実がすべて調査記録までたどれるか（言い換えの途中で出典のない断定が紛れ込んでいないか）。結論を支える事実が修正で文書から抜けていないか。抜けていたら黙って直さず、「この事実が落ちた」と利用者に報告する
- 置き場の既定は、文書と同じ場所の `<文書名>.research.md`。ローカルルールで変えられる

### 出力先（作者の判断）

次の優先順で決め、書いた場所を返答で必ず伝える。

1. 依頼で示された場所
2. 既存の文書の修正なら、その文書の場所
3. ローカルルールで指定した置き場
4. プロジェクトの慣習（`docs/` 配下に同じ種別の文書があるなど）
5. どれにも当たらなければ `docs/<種別>/YYYY-MM-DD-<テーマ>.md`

ツール専用の隠しディレクトリやリポジトリの外は既定にしない。人に読ませる文書なので、見つけやすく、共有・レビューできる場所に置く。

### 共通ルール

種別を問わず、すべての文書に当てる規則。今の tech-writing の文章術を土台にし、次を加える。

ビジネス文書から:

- ピラミッド構造。結論を頂点に置き、根拠を漏れなく重なりなく並べ、各根拠を詳細に分解する（作者の好み「概要から詳細へ」）
- 冒頭の要約。最初の数行だけで、読者が判断や行動に必要なことを受け取れるようにする
- 導入は 状況 → 問題 → 問い → 答え の順。背景は答えにつながる分だけ書く

論文から:

- この文書が答える問いを冒頭で示す
- 事実（調べた結果）と解釈（そこから言えること）を分ける
- 限界（調べていない範囲、前提が崩れる条件）を書く
- 用語は初出で定義する

見出し（作者の判断: メッセージ型）:

- 見出しは、その節の結論を言い切る短い文にする（例:「推奨は案 B。移行費用が最も小さい」）
- 疑問形・呼びかけ・比喩・煽りは使わない
- 「関連文書」「未決事項」「付録」のような定型の節は名詞の見出しのままにする（私の判断）

ユビキタス言語:

- 語は、上流文書・コード・用語集・利用者の発話から取る。比喩や言い換え、独自の造語は使わない
- 既存の語で言えない概念が要るときは、合意フェーズで提案し、合意を得てから使う
- 同じ概念は文書全体で同じ語で呼ぶ

根拠（作者の判断）:

- 調べるときは、可能な限り一次情報（公式ドキュメント、コード、原典の社内文書、元データ）に当たる。要約・検索結果のスニペット・記憶で書かない
- 調べた事実には出典を付け、読者が記載の正当性を後から自分で確かめられるようにする。書き方は今の `references/citation-rules.md` に従う
- 種別を問わず、調べた事実を含む文書すべてに当てる。今は調査資料と DesignDoc に限っている適用範囲を広げる

参照（作者の好み、ただし一般則として本体に置く）:

- 要件や論点に ID を振って、ID で参照しない。短い名前で呼び続ける。読者に前後の行き来をさせないため

今の検討資料スキルにある「見出しは名詞句」は、メッセージ型に置き換える。

### 種別

最初に reference を用意する種別は次の 7 つ（作者の判断: 一旦この範囲）。reference が持つのは、その種別に固有の必須情報・たたき台の目次・下流に渡すものだけ。並び順を押しつけず、合意フェーズで目的に合わせて組み替えてよい。

- Brief（なぜやるか）
- PRD（何を提供するか）
- DesignDoc（どう作るか）
- 開発スケジュール（いつ何を出すか）
- 検討資料（調査をもとに何かを決める）。案を比べる型に加えて、事実 → 要件 → ギャップの型も持つ
- 打ち合わせ資料（叩き台、アジェンダ、相手に聞く質問事項）
- 依頼書（他の人やチームに作業を渡す）

Brief〜検討資料は今の各スキルの内容を移す。打ち合わせ資料と依頼書は、必須情報とたたき台の目次だけの最小限で始める。

### ローカルルール（作者の判断）

3 層に重ね、プロジェクト > 利用者 > プラグイン の順で優先する。

1. プラグイン本体（公開）: 共通ルール・種別の reference・合意フェーズ
2. 利用者のローカル: プラグインの設定で指定するディレクトリ。今の `org_templates_dir` を置き換える。未設定なら `${CLAUDE_PLUGIN_DATA}`（`~/.claude/plugins/data/<id>/`。更新では消えず、アンインストールで消える）を使い、最初に書き込んだときに「設定でディレクトリを指定すると、アンインストールしても残る」と一度だけ知らせる（私の判断。出典: https://code.claude.com/docs/en/plugins-reference §Environment variables、2026-11-04 確認）
   - `style.md`: 利用者の好み
   - `glossary.md`: 用語集
   - `templates/<種別>.md` と `templates/<種別>.guide.md`: 会社のテンプレートと記載ガイド（今の仕組みと同じ）
   - `types/<種別>.md`: プラグインに無い種別の追加（私の判断）
   - `promote-candidates.md`: 本体に昇格する候補（下の「指摘の取り込み」）
3. プロジェクトのローカル: リポジトリ内に置く用語集・好み・テンプレート。ドメインの語はプロジェクトごとに違うため（私の判断）。コミットしてチームで共有するものとして扱い、dev-docs は読むだけにする。書き込むのは利用者に確認したときだけ（作者の判断）

ローカルが持つのは差分（上書きと追加）だけ。スキルを丸ごと複製する使い方は README で禁じる。

### 指摘の取り込み（作者の判断）

セッション中に書き方の指摘を受けたら、文書を直すのと同時に、指摘を次の 4 つに振り分ける。

- この文書だけの話（例:「この節は削って」）: 取り込まない
- 利用者の好み（例:「ID を振らないで」）: 利用者ローカルの `style.md` に追記する
- ドメインの語（例:「その言い方ではなく『〜』と呼んでいる」）: 利用者ローカルの `glossary.md` に、プロジェクト別の節を作って追記する。チームの共有ファイルを黙って書き換えないため、プロジェクトの用語集には自動で書かない。プロジェクトの用語集があるときは「チームの用語集にも載せますか」と聞き、了承を得たら書く（作者の判断）。どのプロジェクトの節に書くかは、作業中のリポジトリ名で決める（私の判断）
- 誰にでも効く一般則: 利用者ローカルの `promote-candidates.md` に追記する。本体は公開リポジトリなので自動では書き込まず、作者が公開前レビューを通して取り込む

確認を挟まずに書き込み、返答の末尾で「好みに追加: 〜」と 1 行で知らせる。利用者が取り違いを指摘したら消す。

- 1 項目は「規則 + なぜ + 指摘を受けた例」で書く
- 既存の項目と重なれば統合し、矛盾すれば書き込まずに利用者に聞く
- 項目が増えて読み込みが重くなったら、統合の整理を提案する（目安 30 項目。私の判断）

dev-docs が呼ばれていないターンの指摘は拾えない。発火の改善を先に行う理由の 1 つ。

旧版が頼っていた別配布の改善記録のスキルへの依存は外し、取り込みをプラグインの中で完結させる。

## 移行

- 旧スキルの `/dev-docs:brief` などのスラッシュコマンドは廃止する。互換のための別名は置かない（私の判断。作者以外の利用はほぼ無く、別名を残すと発火の競合が起きるため）
- プラグインのバージョンは 0.3.0 に上げる（私の判断。1.0 前なので破壊的変更を許す）
- `org_templates_dir` を使っていた利用者のテンプレートは、新しい設定のディレクトリの `templates/` に置き直せば読める。README に移行手順を 3 行で書く
- `references/citation-rules.md` `references/source-intake.md` `references/doc-chain.md` は残す。`doc-chain.md` の表にある `/dev-docs:<種別>` の記述は種別名に直す

## 評価

- 発火: スキルの `evals/trigger.json` を 1 本にまとめ、`claude -p` で確かめる。使うべき依頼として、今回取りこぼしていた型（打ち合わせの叩き台、相手に聞く質問事項、依頼書、既存資料の構成の手直し、調査結果の資料化）を一般化して入れる。使うべきでない依頼として、個人用 wiki への記録、文の自然さだけの手直し、コードの変更、翻訳を入れる。例文に業務固有の語を入れない
- 結果: 代表的な依頼（新規の検討資料、打ち合わせ資料、小さな修正、レビュー、書き方の指摘を含む往復）で実行し、次を確かめる。新規では合意フェーズが出る / 小さな修正では出ない / 表現だけの修正で調査記録が変わらず、結論を支える事実と出典が文書に残る / 見出しがメッセージ型で、ブログ調の見出しが無い / ID 参照が無い / 指摘が `style.md` に追記され、返答で知らされる
- 構造: `bash tests/validate.sh` と `bash tests/git-hooks.test.sh`

## 作り手に任せること

- スキルの名前（仮に `dev-docs:doc`）。発火の評価で決めてよい
- SKILL.md と references の分け方。SKILL.md は流れと読み込む reference の指示に絞り、共通ルール・合意フェーズの書式・自己レビュー・取り込み・ローカルルールの読み方は references に置く想定
- 合意フェーズで示すメッセージの具体的な書式
- プロジェクトのローカルの置き場（`.claude/dev-docs/` などのリポジトリ内のパス）
- 種別の判定に迷ったときの扱い（利用者に聞くか、共通ルールだけで進めるか）
