# dev-docs: スキル名を write にし、発火の範囲を広げる

- 作成日: 2026-11-04
- ステータス: 作者の承認済み
- 対象: `plugins/dev-docs/`

## 要約

スキル名を `doc` から `write` に変え、0.5.0 とする。あわせて、開発にまつわる文書の作成・更新・推敲のすべてで呼ばれるように発火の範囲を広げる。新しく対象に入れる commit message・PR 説明・エージェント向けの指示・コードコメントは「付随文書」として扱い、合意フェーズ・調査記録・下流チェックを回さない軽い流れで書く。

## なぜ変えるか

- 名前: 呼び出しは常に `dev-docs:<スキル名>` になる。プラグイン名がすでに「docs」と言っているので、`doc` は情報を足さない。Anthropic のスキル作成ガイドも、`documents` のような汎用すぎる名前を避け、動作を表す名前にするよう勧めている
- 発火: 既存の文書の更新・追記・最新化の依頼で呼ばれにくい。description が挙げていたのは「構成を直す・推敲する・冗長さを削る・レビュー」だけだった。種類の一覧も、例ではなく限定に読めた
- 範囲: 作者は、commit message・PR 説明・CLAUDE.md などの文面も同じ書き方の規則で書きたい

## 目標

- 開発にまつわる文書の新規作成・更新・追記・推敲・構成の直し・レビューの依頼で呼ばれる。種類の一覧にない文書（仕様書・リリースノート・運用手順など）も含む
- 付随文書の文面を書く・直す依頼で呼ばれ、合意フェーズに入らずに書く
- 付随文書を伴う操作の依頼（「コミットして push して」「PR を作って」）では呼ばれない

## やらないこと

- 個人用ナレッジやメモ、文の自然さだけの手直し、社外向けの記事・ブログは、引き続き対象外にする。個人用ナレッジは書式が違い、持ち込むと他人に渡す文書が崩れる。自然さだけの直しには、構成と事実を確かめる流れが重すぎる。社外向けの記事は導入から入る構成が正当で、共通ルールと衝突する
- 旧名 `doc` の別名は残さない。0.3 で旧 6 スキルを消したときと同じ扱いにする

## 決めたこと

### 付随文書の扱い

付随文書は、文書の種別（`brief` など）とは別に判定する。対象は次の 4 つ。

- commit message
- PR 説明
- エージェント向けの指示（CLAUDE.md・AGENTS.md・SKILL.md など）
- コードコメント

付随文書では、合意フェーズ・調査記録・下流チェックを回さない。どれも短く、形はリポジトリの規約で決まっていて、書く事実は差分とコードから取れるためだ。そのかわり、次の 3 つは必ず回す。

- 書く前に、リポジトリの規約を読む（PR テンプレート、`git log` の書きぶり、CLAUDE.md、コメントの方針、ローカルルール）
- 書いた内容を差分・コードと突き合わせる
- 共通ルールのうち文のレベルのもの（結論先行、一文一義、削れる語は削る、AI 臭）を当てる。ピラミッド構造や見出しの型は当てない

種類ごとの規則は `references/attached-text.md` に書く。

### 発火の境界

文面そのものを書く・直す依頼で呼ばれ、文面を伴う操作の依頼では呼ばれないようにする。操作の依頼で呼ばれると、commit や PR 作成の流れに割り込み、そのたびにスキルを読み込むことになる。

### 評価

- 発火: 更新・追記の依頼、一覧にない文書、付随文書 4 種類を正例に足す。「今の変更内容でコミットメッセージを書いて」は負例から正例に移す。操作の依頼（「コミットして push して」「PR を作って」）を負例に足す
- 結果: 付随文書で合意フェーズに入らないこと、リポジトリの規約を読むことを確かめるケースを足す
